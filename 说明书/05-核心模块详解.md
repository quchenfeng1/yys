## 第五部分 核心模块详解

### 5.1 设备连接模块（device/adb_client.py）

**职责**：封装 ADB 连接与底层设备操作，对上层屏蔽 ADB 命令细节。

**核心接口**：

```python
class ADBClient:
    def __init__(self, device_id: str = "127.0.0.1:5555")
    def connect(self) -> bool                    # 连接设备
    def is_connected(self) -> bool               # 检测连接状态
    def screenshot(self) -> np.ndarray           # 截图，返回 OpenCV 图像
    def click(self, x: int, y: int)              # 点击坐标（仅坐标，不含防封）
    def swipe(self, x1, y1, x2, y2, duration)    # 滑动
    def input_key(self, key: str)                # 按键（BACK/HOME/MENU）
    def get_screen_size(self) -> tuple           # 获取屏幕分辨率
```

**说明**：
- 支持 ADB 端口配置（雷电 5555、MuMu 7555、夜神 62001 等）。
- 截图采用 `adb exec-out screencap -p` 直接输出二进制流，避免文件读写延迟。
- 提供 ADB 后台点击（`input tap`）与前台点击（pyautogui）两种模式，可配置切换。

### 5.2 图像识别模块（core/recognizer.py）

**职责**：在截图中定位目标图片，返回匹配位置与置信度。

**核心接口**：

```python
class Recognizer:
    def find(self, template_name: str, region=None, threshold=0.8) -> MatchResult | None
    def find_all(self, template_name: str, region=None, threshold=0.8) -> list[MatchResult]
    def exists(self, template_name: str, threshold=0.8) -> bool
    def wait(self, template_name: str, timeout=10, interval=0.5) -> MatchResult | None
    def wait_any(self, template_names: list, timeout=10) -> tuple[str, MatchResult] | None

class MatchResult:
    name: str          # 模板名
    center: tuple      # 中心坐标 (x, y)
    topleft: tuple     # 左上角坐标
    size: tuple        # 匹配区域大小
    confidence: float  # 置信度 0~1
```

**识别策略**：
- **主用模板匹配**（`cv2.matchTemplate` + `TM_CCOEFF_NORMED`）：速度快、精度高，要求素材与界面像素一致（故统一 1280×720 分辨率）。
- **备选特征点匹配**（ORB/SIFT）：分辨率变化时使用，容差大但速度慢。
- **灰度匹配**：默认转灰度图匹配，提升速度；颜色敏感场景可开启彩色匹配。
- **区域限定**：支持 `region=(x, y, w, h)` 限定搜索范围，加速识别并减少误匹配。
- **多尺度匹配**：针对可能缩放的 UI，支持金字塔多尺度搜索（可选开关）。

**素材加载机制**：
- 启动时递归扫描 `assets/` 全部 PNG，按相对路径建立索引（如 `common/battle/challenge_btn`、`scenes/login/enter_game`、`tasks/permanent/yuhun/entry`）。
- 支持多层目录结构（common/scenes/tasks/teams 四层分类），索引名用 `/` 分隔。
- 使用 PIL 读取图片（兼容中文路径），预转灰度并缓存到内存，避免重复 IO。
- 素材更新后调用 `recognizer.reload()` 重新加载。

### 5.3 操作执行模块（core/executor.py）

**职责**：封装所有用户操作（点击、滑动、按键），**强制经过防封号引擎处理**。这是防封号的关键守门人。

**核心接口**：

```python
class Executor:
    def click_image(self, template_name: str, region=None, timeout=10) -> bool
        # 识别图片 → 防封号计算偏移 → 自然移动 → 点击
    def click_point(self, x: int, y: int)
        # 直接坐标点击（仍经防封号偏移）
    def click_if_exists(self, template_name: str, threshold=0.8) -> bool
        # 存在则点击，不存在则跳过
    def swipe(self, x1, y1, x2, y2, duration=None)
        # 滑动（duration 随机化）
    def long_press(self, x, y, duration=None)
        # 长按
    def input_text(self, text: str)
        # 输入文本（用于账号密码）
    def random_sleep(self, min_s=1.0, max_s=3.0)
        # 随机等待
```

**关键约束**：
- **任务层禁止绕过此模块直接调用 ADB click**。`Executor` 内部在每次点击前调用 `AntiDetect` 生成随机偏移与延迟，并模拟自然鼠标轨迹。
- 识别失败时自动重试（默认 3 次），仍失败则记录日志并返回 False，不崩溃。

### 5.8 阵容御魂管理模块（core/team_manager.py）★ 核心服务

**职责**：统一管理所有战斗的"阵容 + 御魂"配置与调整。是**跨模块共享服务**，所有战斗模块（DungeonTask / SpecialTask / 日常战斗）在开战前调用它完成阵容准备，避免每个副本各自实现一套阵容逻辑。

**设计动机**：阴阳师不同副本所需阵容差异极大（御魂本要输出队、觉醒本要刷材料队、真蛇要特殊阵容），且**调整阵容/御魂必须在对局外完成，选阵容在对局内完成**。将这套流程收口到单一模块，使每个副本只需声明"我要用哪套预设"，其余交给 TeamManager。这与防封号、可维护性两大原则高度一致：阵容操作集中走 Executor 自动叠加防封号；阵容预设与代码分离，版本更新只改配置。

**核心接口**：

```python
class TeamManager:
    def ensure_team(self, team_id: str) -> bool:
        """主入口（对局外）：确保当前已装备指定阵容预设。
        - 幂等：verify_current_team 已匹配则直接返回 True，不重复操作
        - 不匹配则调用 adjust_team_outside 进行调整
        - 返回 False 表示调整失败（素材缺失/超时）"""

    def adjust_team_outside(self, team_id: str) -> bool:
        """对局外调整：庭院 → 式神录 → 切换目标阵容编队 → (需调御魂?) adjust_mitama → 返回庭院"""

    def adjust_mitama(self, mitama_presets: list) -> bool:
        """对局外御魂调整：进入御魂界面，按预设套装给指定式神装配御魂"""

    def select_team_in_battle(self, team_id: str) -> bool:
        """对局内选阵容：副本开始前的阵容选择界面，选中目标预设阵容"""

    def lock_team(self) -> bool:
        """锁定阵容：点击"锁定阵容"按钮，锁定后重复刷取不再弹选阵容界面"""

    def verify_current_team(self, team_id: str) -> bool:
        """校验当前装备阵容是否为目标预设（识别阵容标记图 team_id/marker）"""

    # 预设管理
    def register_preset(self, team_id: str, config: dict): ...
    def get_preset(self, team_id: str) -> dict: ...
    def list_presets(self) -> list: ...
```

**两阶段阵容流程**（核心设计）：

```
┌──────────────────────────────────────────────────────────┐
│ 阶段一：对局外调整（进入副本前，在庭院/式神录完成）        │
│   ensure_team(team_id)                                   │
│   ├─ verify_current_team → 已匹配? 直接返回 True          │
│   └─ adjust_team_outside                                 │
│      ├─ 庭院 → 式神录                                    │
│      ├─ 切换到目标阵容编队                               │
│      ├─ (需调御魂?) adjust_mitama → 御魂界面装配          │
│      └─ 返回庭院                                         │
├──────────────────────────────────────────────────────────┤
│ 阶段二：对局内选择（首次进入副本，选阵容界面）             │
│   select_team_in_battle(team_id)                         │
│   ├─ 识别阵容选择界面                                    │
│      ├─ 滑动/点击选中目标阵容                            │
│   ├─ lock_team() → 锁定阵容（lock_after_select=true 时）  │
│   └─ 后续重复刷取不再触发选阵容（已锁定，直接挑战）       │
└──────────────────────────────────────────────────────────┘
```

**阵容检查的强制性** ★（用户确认）：
- **每个战斗任务首次进入战斗之前，必须检查阵容**——这是强制环节，不可跳过。`pre_check_team()` 检测当前阵容是否匹配目标预设，不匹配则必须走 `ensure_team()` 调整。
- **首次进入战斗时切换阵容**：在选阵容界面执行 `select_team_in_battle()`。
- **锁定与否在副本配置中设定**：副本配置（`config/coords/<dungeon>.json`）的 `lock_team_after_select` 字段控制选阵容后是否锁定。
  - `lock_team_after_select: true` → 选阵容后锁定，后续重复刷取不再弹选阵容界面（减少操作、降低风控）。
  - `lock_team_after_select: false` → 不锁定，每次进入副本都需选阵容（适用于阵容需频繁切换的场景）。
- **已锁定则跳过选阵容**：`loop()` 阶段检测到阵容已锁定，直接走"挑战→结算"循环，不再触发选阵容。

**与防封号的关系**（重点）：阵容调整涉及大量界面跳转和长操作，属"高风险长流程"。TeamManager 内部所有操作必须经过 Executor（自动叠加防封号），并额外约束：
- 每步界面切换后强制 **1.5~3s 随机等待**（界面加载慢，过快易被检测）
- 御魂装配每次操作间 **0.8~2s 随机间隔**
- 单次完整阵容调整上限 **90s**，超时告警并中止
- **幂等校验**：同一阵容不重复调整，避免无意义操作堆积行为特征

**素材规范**：`assets/teams/<team_id>/` 存放该预设的识别标记图与各步骤截图；`config/coords/teams/<team_id>.json` 存放阵容预设配置（结构见 [07-资源与配置管理](07-资源与配置管理.md) 7.2）。

**预设配置结构示例**：

```json
{
  "team_id": "yuhun_speed",
  "name": "御魂·输出队",
  "shikigami": ["山兔", "座敷", "茨木", "大天狗", "晴明"],
  "mitama_presets": [
    {"shikigami": "茨木", "set": "破势", "slots": "246攻攻暴", "sub_stats": "暴击伤害"},
    {"shikigami": "大天狗", "set": "针女", "slots": "246攻攻暴", "sub_stats": "暴击"}
  ],
  "lock_after_select": true,
  "verify_image": "teams/yuhun_speed/marker",
  "adjust_outside_first": true
}
```

### 5.9 任务调度与时间控制模块（core/scheduler.py）★ 核心服务

**职责**：统一管理所有任务的时间规则、优先级与执行顺序，生成每日日程表。所有任务模块（日常/常驻/活动/特殊）均**据此日程表先后调用**，与具体任务逻辑完全解耦。这是用户明确要求"独立于各个模块之外"的调度中枢——任务自身只管"怎么做"，调度器决定"何时做、谁先做、做几次"。

**设计动机**：阴阳师任务有严格的时间窗口（逢魔 17-22 点、悬赏每日刷新、真蛇周末开放、活动限时等），且多任务可能同时到期。集中管理时间与顺序可避免每个任务各自判断时间造成逻辑散乱与冲突，也让新增任务时只需声明时间规则即自动纳入调度。

**更关键的动机——"下次执行时间"**：很多任务并非"开窗即可做"，而是"做过之后要等一段时间才能再做"。例如：每日签到今天做过，明天 00:00 前都不该再做；好友寄养 6 小时一次；结界卡挂上后要等它失效才能重挂。这类任务如果只靠窗口判断，脚本每次重启都会重复执行，既浪费又可能触发风控。因此本模块参考碧蓝航线脚本 alsa 的设计，引入 **next_run_time（下次执行时间）** 作为调度的核心判据：调度器为每个任务维护一个"下次最早可执行时刻"，只有 `当前时间 ≥ next_run_time` 且在时间窗口内才真正执行；执行成功后按 RepeatRule 推进 next_run_time，并**持久化到磁盘**，重启脚本也不丢失。

**核心概念**：

| 概念 | 说明 |
|------|------|
| **RepeatRule（执行规则）** ★ | 每个任务的"何时执行、如何重复"的统一配置。包含执行方式（单次/每日/每周/每月/隔N天/隔N小时/依赖失效时间）、执行时刻、执行次数。**所有任务都必须配置**（常驻副本也不例外） |
| **next_run_time（下次执行时间）** ★ | 任务"最早可执行的下一时刻"。只有 `now ≥ next_run_time` 才有资格被执行。这是 alsa 式调度的核心判据，解决"做过就不再重复做"的问题。**所有任务都拥有此属性，且在 UI 可见可改** |
| **time_window（时间窗口，可选）** | 部分任务有"只能在某时段做"的硬约束（如逢魔 17-22 点）。作为 RepeatRule 的可选字段约束可执行时段；无此约束的任务不配 |
| **TaskState（执行记录）** ★ | 每个任务的运行时状态（last_run_time / next_run_time / success_count / expire_at 等），持久化到 `config/runtime/task_state.json`，重启恢复 |
| priority（优先级） | 数字越小越优先；同时到期时优先级小者先执行 |
| default_order（默认顺序） | 同优先级任务的执行顺序，可在配置中调整（如日常类整体优先于副本类） |
| Schedule（日程表） | 调度器扫描所有启用任务，结合 RepeatRule 与 next_run_time 生成当前可执行队列 |
| times / max_daily（次数控制） | 单次执行次数 / 每日上限 / 总次数上限 / 冷却间隔（与 RepeatRule.times 配合） |

> **统一模型说明**：v1.4 的 TimeRule（窗口）+ run_strategy（推进策略）两个概念，在 v1.5 合并为单一的 **RepeatRule**。这样每个任务只需配一套执行规则，调度器据此自动计算 next_run_time 并在执行成功后推进，逻辑更清晰，且让常驻副本（御魂、觉醒等）也能精确控制"每周几几点刷几次"。

**执行规则（RepeatRule）类型** ★：

```python
class RepeatRule:
    type: str            # once / daily / weekly / monthly / interval_days / interval_hours / expire_at
    at_time: str = None  # 执行时刻 "HH:MM"（daily/weekly/monthly/interval_days 用）
    weekdays: list = None    # weekly：[1,3,5]（1=周一...7=周日）
    month_days: list = None  # monthly：[1,15]
    days: int = None         # interval_days：隔 N 天
    hours: float = None      # interval_hours：隔 N 小时
    at: str = None           # once：完整时间 "2026-08-01T10:00:00"
    times: int = 1           # 单次调度执行次数（如御魂刷 30 次）
    window: dict = None      # 可选时间窗口 {start:"17:00", end:"22:00"}
```

七种执行方式及 next_run_time 推进规则：

| type | 含义 | 执行成功后推进 next_run_time | 典型任务 |
|------|------|------------------------------|----------|
| `once` | 单次任务，指定日期时间 | 不推进（标记完成，不再执行） | 一次性活动、临时补刷 |
| `daily` | 每日指定时刻执行 | 次日 at_time | 签到、悬赏、花合战、地域鬼王、逢魔 |
| `weekly` | 每周指定周几的指定时刻 | 下个匹配 weekday 的 at_time | 每周分享、御魂（可设周一三五刷）、真蛇周末 |
| `monthly` | 每月指定几号的指定时刻 | 下个匹配 month_day 的 at_time | 月初领奖、月卡 |
| `interval_days` | 隔 N 天的指定时刻执行 | (今日+N天) 的 at_time | 某些 3 天一次的任务 |
| `interval_hours` | 隔 N 小时执行一次 | now + hours | 好友寄养（6h，可在 UI 改）、结界突破冷却 |
| `expire_at` | 依赖外部失效时间 | 不自动推进，由任务内 `report_expire()` 上报 | 结界卡（识图识别剩余时间后上报） |

**配置示例**：

```yaml
# 每日签到：每天 00:00 后可做，做一次锁到次日
- name: "sign_in"
  repeat: { type: "daily", at_time: "00:00", times: 1 }

# 好友寄养：隔 6 小时一次（hours 可在 UI 修改）
- name: "friend_foster"
  repeat: { type: "interval_hours", hours: 6, times: 1 }

# 结界卡：依赖失效时间，任务内识图识别后上报
- name: "kekkai_card"
  repeat: { type: "expire_at", times: 1 }

# 御魂副本：每周一三五 14:00 刷 30 次（常驻副本也精确控时）
- name: "yuhun"
  repeat: { type: "weekly", weekdays: [1,3,5], at_time: "14:00", times: 30, max_daily: 100 }

# 逢魔之时：每天 17:00-22:00 窗口内做一次
- name: "fengmo"
  repeat: { type: "daily", at_time: "17:00", times: 1, window: { start: "17:00", end: "22:00" } }
```

> **所有任务都必须配 `repeat`**。无明确时间偏好的常驻副本可配 `daily` + at_time，或由用户在 UI 设定。`window` 仅对有硬时段约束的任务（逢魔、斗技等）使用。
>
> **next_run_time 的可见可改性**：每个任务的 next_run_time 都在 UI 任务行显示（含倒计时），并支持手动修改——用户可把某任务"提前到现在"立即执行，或"推迟到某时刻"跳过当前轮次。修改后立即持久化到 task_state.json。

#### 5.9.1 下次执行时间机制（next_run_time）★ 重点

**双重判据**：一个任务能否在当前时刻执行，必须同时满足两个条件：

```
可执行 = (now ≥ next_run_time)  AND  (window 为空  OR  now 在 window 时段内)
```

- **next_run_time**（由 RepeatRule 决定）定义"最早可做的时刻"。
- **window**（可选）定义"允许的硬时段"（如逢魔 17-22 点）；无硬时段约束的任务 window 为空，只要 next_run_time 到了就能做。
- 两者缺一不可：即使到了 18 点（在窗口内），若 next_run_time 是明天 00:00（今天已做过），也不会执行。

**执行成功后的推进**：调度器根据任务的 RepeatRule.type 自动计算并推进 next_run_time：

| type | 推进规则 |
|------|----------|
| `once` | 不推进，标记 `completed=true`，不再调度 |
| `daily` | next_run_time = 次日 at_time |
| `weekly` | next_run_time = 下个匹配 weekdays 的 at_time |
| `monthly` | next_run_time = 下个匹配 month_days 的 at_time |
| `interval_days` | next_run_time = 今日 + days 天 的 at_time |
| `interval_hours` | next_run_time = now + hours 小时 |
| `expire_at` | 不自动推进，等待任务内 `self.report_expire(失效时刻)` 上报后设为该时刻 |

> 即：**下次执行时间已到则立即执行，执行后若非单次（once），则按规则重新计算 next_run_time**。这正是用户要求的执行逻辑。

**重置时刻**：默认 `reset_at = 00:00`（阴阳师游戏的每日重置时间）。`daily`/`weekly`/`monthly` 类型在跨过 00:00 时重置 `today_count` 并重新评估当日窗口。如某任务需跟随其他刷新点，可在全局设置或任务配置中改 `reset_at`，但默认 00:00 即符合阴阳师规则。

**结界卡的特殊处理**：结界卡的失效时间通过**识图识别**游戏内结界卡剩余时间获得，属于结界卡任务自身的识图逻辑（在 `run()` 内完成识别后调用 `self.report_expire(识别到的失效时刻)`）。调度器不关心失效时间怎么来，只接收任务上报的值并据此设置 next_run_time。因此结界卡任务**单独处理**识图部分，与调度模块解耦。

**times 与 max_daily 的配合**：
- `RepeatRule.times`：单次调度（next_run_time 到期后这一次调度）内执行的次数，如御魂刷 30 次。
- `max_daily`：每日累计上限，防止超量（如结界突破每日最多 9 次）。
- 对 `daily`/`weekly` 等类型，times 通常为 1（每日做一次领奖）；对常驻副本，times 可大于 1（一次调度刷多把）。

#### 5.9.2 执行记录持久化（TaskState）★ 重点

next_run_time 必须跨重启保留，否则脚本重启后所有任务都会被当作"未做过"重新执行。因此调度器维护一份**执行记录文件**：

**文件位置**：`config/runtime/task_state.json`（runtime 目录不入版本库，脚本自动创建维护）

**文件结构**：

```json
{
  "_version": 1,
  "_updated_at": "2026-07-18T21:00:00+08:00",
  "tasks": {
    "sign_in": {
      "last_run_time": "2026-07-18T08:12:00+08:00",
      "last_success": true,
      "next_run_time": "2026-07-19T00:00:00+08:00",
      "success_count": 1,
      "expire_at": null
    },
    "friend_foster": {
      "last_run_time": "2026-07-18T15:00:00+08:00",
      "last_success": true,
      "next_run_time": "2026-07-18T21:00:00+08:00",
      "success_count": 3,
      "expire_at": null
    },
    "kekkai_card": {
      "last_run_time": "2026-07-18T10:00:00+08:00",
      "last_success": true,
      "next_run_time": "2026-07-18T22:00:00+08:00",
      "success_count": 1,
      "expire_at": "2026-07-18T22:00:00+08:00"
    },
    "yuhun": {
      "last_run_time": "2026-07-18T14:00:00+08:00",
      "last_success": true,
      "next_run_time": null,
      "success_count": 30,
      "today_count": 30,
      "expire_at": null
    }
  }
}
```

**字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `last_run_time` | datetime | 上次执行时刻（不论成败） |
| `last_success` | bool | 上次执行是否成功 |
| `next_run_time` | datetime / null | 下次最早可执行时刻；null 表示无限制（按窗口+次数判断） |
| `success_count` | int | 累计成功次数（用于 max_total 上限判断） |
| `today_count` | int | 今日已执行成功次数（用于 max_daily，每日 00:00 重置） |
| `expire_at` | datetime / null | 任务上报的"外部失效时间"（结界卡失效、寄养结束等），expire_at 策略下即 next_run_time 来源 |

**持久化时机**：

- `mark_done(task, success=True)` → 更新 last_run_time / next_run_time / success_count / today_count，**立即写盘**。
- 任务通过 `self.report_expire(expire_at)` 上报失效时间 → 更新 expire_at 与 next_run_time，立即写盘。
- 脚本启动时 `load_state()` 读取该文件恢复内存状态；文件不存在或损坏时重建空状态（不阻断启动）。
- 每日 00:00（默认 reset_at）调度器自动重置所有任务的 `today_count=0`，并对 daily/weekly/monthly 任务重新评估当日窗口。

**安全性**：写盘采用"写临时文件 → 原子替换"策略，避免中途崩溃导致记录损坏。文件含 `_version` 字段便于后续迁移。

**核心接口**：

```python
class Scheduler:
    def load_state(self) -> TaskState:
        """启动时从 config/runtime/task_state.json 恢复执行记录；文件缺失则建空状态"""

    def save_state(self):
        """将内存中的执行记录原子写盘（写临时文件→替换）"""

    def build_daily_schedule(self, date=None) -> list:
        """扫描所有启用任务，结合 RepeatRule 与 next_run_time 生成当前可执行队列，
           按 priority→default_order 排序"""

    def get_next_task(self):
        """获取当前时刻应执行的下一个任务：
           满足 (now ≥ next_run_time) AND (now 在窗口内) AND (未达次数上限) 的最高优先级任务"""

    def is_due(self, task_name: str, now=None) -> bool:
        """判断任务是否到期：now ≥ next_run_time 且（无 window 或在 window 窗口内）"""

    def get_next_run_time(self, task_name: str) -> datetime:
        """读取任务的下次执行时间（供 UI 展示"距下次执行还剩 XX"）"""

    def mark_done(self, task_name: str, success: bool = True):
        """标记任务执行完成：更新 last_run_time/last_success/计数，
           并按 RepeatRule.type 推进 next_run_time；success=True 才推进，
           失败时不推进（next_run_time 保持，允许重试）；立即 save_state()"""

    def update_next_run(self, task_name: str, next_run_time: datetime):
        """手动设置任务的下次执行时间（UI 修改 next_run_time 或点"跳过本次"时调用）"""

    def report_expire(self, task_name: str, expire_at: datetime):
        """任务执行中上报外部失效时间（如结界卡失效时刻），
           调度器据此设置 next_run_time = expire_at，并写入 state.expire_at"""

    def resolve_conflict(self, tasks: list) -> list:
        """冲突仲裁：多任务同时到期时，按 priority 升序，同优先级按 default_order"""

    def check_times_limit(self, task_name: str) -> bool:
        """检查任务是否未达次数上限（times / max_daily / max_total / cooldown / today_count）"""

    def reset_daily_counters(self):
        """每日 00:00（默认 reset_at）重置所有任务 today_count=0；
           daily/weekly/monthly 任务在重置后重新评估当日窗口"""

    def register_task(self, name: str, repeat: RepeatRule, priority: int, **kw):
        """注册任务到调度器（自动注册时由扫描器调用）；repeat 为该任务的执行规则"""
```

> **失败不推进原则**：`mark_done(success=False)` 不推进 next_run_time，任务保持"到期可重试"状态，由调度器在下一轮按优先级重新尝试（受重试次数与防封号限制约束）。这保证临时性失败（如网络抖动、识别不到）不会让每日一次的任务被跳过。

**日程表生成与执行流程**：

```
脚本启动
  │
  ├─[0] load_state() → 从 task_state.json 恢复各任务的 next_run_time / today_count / success_count
  ├─[1] 扫描所有 enabled=true 的任务，读取各自 RepeatRule
  ├─[2] 过滤：剔除不在当日时间窗口的任务（如周末才开放的真蛇、window 不匹配的逢魔）
  ├─[3] 过滤：剔除已过期的活动任务（valid_until < today）
  ├─[4] 过滤：剔除 now < next_run_time 的任务（未到下次执行时间）★
  ├─[5] 排序：按 priority 升序 → 同优先级按 default_order
  └─[6] 生成当前可执行 Schedule 队列
         │
循环执行：
  ├─ get_next_task() → 取队首任务（满足 双重判据 + 未达次数上限）
  ├─ check_times_limit() → today_count / success_count 未达上限才执行
  ├─ 任务 execute()
  │    ├─ 成功 → mark_done(success=True) → 按 RepeatRule.type 推进 next_run_time → save_state()
  │    ├─ 失败 → mark_done(success=False) → 不推进 next_run_time（允许重试）→ save_state()
  │    └─ 任务可调 self.report_expire(expire_at) 上报失效时间 → 更新 next_run_time
  └─ 队列空 或 触发每日运行上限 → save_state() → 收尾退出

每日 00:00（或 reset_at）定时触发：
  └─ reset_daily_counters() → 所有任务 today_count=0，daily/weekly/monthly 任务重新评估窗口
```

**重启后的行为**：脚本关闭再打开，load_state() 恢复记录——今天已签到的任务 next_run_time 仍是明天 00:00，不会重复签到；好友寄养若距上次不足 6 小时，next_run_time 在未来，不会提前寄养。这正是 alsa 式"下次执行时间"控制的核心价值。

**优先级与默认顺序**（重点）：

- **priority**：用户为每个任务设定，数字越小越优先。如签到 priority=1，御魂 priority=10。
- **default_order**：同优先级任务的相对顺序，在 `config/tasks.yaml` 顶层配置。可整体调整大类先后：
  ```yaml
  default_order: ["daily", "permanent", "special", "event"]
  ```
  即同优先级下，日常类任务整体先于常驻副本类执行。
- **冲突示例**：签到(priority=1)与每日领奖(priority=1)同时到期 → 同属 daily 类，按类内注册顺序；御魂(priority=10)与觉醒(priority=10) → 同属 permanent 类，按类内顺序。若用户把签到 priority 调到比御魂更小，则签到必先执行，与 default_order 无关。

**次数控制**：

| 字段 | 说明 |
|------|------|
| `times` | 单次调度执行次数（如御魂刷 30 次） |
| `max_daily` | 每日上限（如结界突破每日最多 9 次） |
| `max_total` | 总次数上限（如某活动总共只能打 50 次） |
| `cooldown` | 两次执行间最小间隔（秒），防止过频 |

**与防封号的协同**：调度器内置每日运行总时长/总操作数上限（见 [08-防封号策略详解](08-防封号策略详解.md) 8.4），达到上限后即使日程表还有任务也强制收尾，避免超时挂机。

**典型场景示例**（RepeatRule 各类型的实际运行）：

| 场景 | type | 配置 | 运行时序 |
|------|------|------|----------|
| 每日签到 | daily | `repeat: {type: daily, at_time: "00:00", times: 1}` | 8:00 执行成功 → next_run_time 推进到次日 00:00 → 当天再开脚本不重复签到 → 次日 00:00 后重新可执行 |
| 好友寄养 | interval_hours | `repeat: {type: interval_hours, hours: 6, times: 1}` | 15:00 寄养成功 → next_run_time = 21:00 → 18:00 开脚本，因 now<21:00 跳过 → 21:00 后自动寄养 → next_run_time 推进到次日 03:00（hours 可在 UI 改） |
| 结界卡 | expire_at | `repeat: {type: expire_at, times: 1}` | 10:00 挂卡，任务内识图识别剩余时间后 `self.report_expire("22:00")` → next_run_time = 22:00 → 22:00 后自动重挂新卡，再识图上报新失效时间 |
| 御魂副本 | weekly | `repeat: {type: weekly, weekdays:[1,3,5], at_time:"14:00", times:30}` | 周一 14:00 到期 → 刷 30 次 → next_run_time 推进到周三 14:00 → 周二开脚本不刷 → 周三 14:00 再刷 |
| 逢魔之时 | daily+window | `repeat: {type: daily, at_time:"17:00", times:1, window:{start:"17:00",end:"22:00"}}` | 17:00 到期且在窗口内 → 执行 → next_run_time 推进到次日 17:00；若 22:01 才开脚本，虽 next_run_time 已过但超出 window，当日跳过 |
| 限时活动 | once | `repeat: {type: once, at:"2026-08-01T10:00:00", times:1}` | 到指定时间执行一次 → 标记 completed → 不再调度 |

> 所有任务的 next_run_time 都在 UI 可见可改，修改后立即持久化。常驻副本（御魂/觉醒等）通过 RepeatRule 精确控制"每周几几点刷几次"，不再只是"随时可执行"。

### 5.10 账号管理与多开模块（core/account_manager.py）★ 核心服务

**职责**：统一管理主号与最多2个小号的账号信息、区服切换、多开模拟器实例绑定。是 v1.7 新增的跨模块核心服务，为调度器和任务层提供"当前操作哪个账号"的上下文。

**设计动机**：用户需要多区切换与多开配合——主号执行全部日常与副本任务，小号仅配合主号刷副本（如组队副本的副号位）。多开意味着每个账号绑定独立模拟器实例（独立 ADB 端口），脚本需在多个设备间切换操作。将账号管理收口到单一模块，避免任务层各自维护设备绑定关系，同时让小号的"只刷副本不跑日常"约束集中生效。

**核心接口**：

```python
class AccountManager:
    def get_main_account(self) -> Account
    def get_sub_accounts(self) -> list[Account]
    def get_active_account(self) -> Account           # 当前正在操作的账号
    def switch_account(self, account_id: str) -> bool  # 切换操作目标到指定账号
    def get_device_for_account(self, account_id: str) -> str  # 获取该账号绑定的ADB设备ID
    def is_sub_account(self, account_id: str) -> bool  # 是否为小号
    def get_task_scope(self, account_id: str) -> list  # 该账号可执行的任务范围
    def add_account(self, account: Account) -> bool    # 新增账号（主号/小号）
    def remove_account(self, account_id: str) -> bool  # 删除账号
    def update_account(self, account_id: str, **kwargs) # 修改账号信息
```

**Account 数据结构**：

```python
@dataclass
class Account:
    account_id: str          # 唯一标识（如 "main", "sub1", "sub2"）
    role: str                # "main" / "sub"（主号/小号）
    nickname: str            # 游戏内昵称（备注用）
    server: str              # 区服名称
    adb_port: int            # 绑定的模拟器 ADB 端口
    device_id: str           # ADB 设备 ID（如 "127.0.0.1:16384"）
    enabled: bool = True     # 是否启用
    # 小号专属：
    dungeon_tasks: list = None  # 小号可执行的副本任务列表（仅 permanent 类）
```

**关键设计**：
- **主号唯一**：系统中只有1个主号（`role="main"`），执行全部日常+副本+特殊任务。
- **小号上限2个**：最多2个小号（`role="sub"`），**只执行副本刷取**（permanent 类），不执行日常（daily）、活动（event）、特殊（special）任务。
- **独立设备绑定**：每个账号绑定独立模拟器实例（独立 ADB 端口），多开时脚本通过 `switch_account` 切换当前操作设备。
- **任务范围约束**：调度器在生成日程表时，根据 `get_task_scope()` 过滤——小号只产出副本类任务，日常/活动/特殊类自动排除。
- **配置持久化**：所有账号信息存储在 `config/accounts.yaml`，UI 修改后立即持久化。
