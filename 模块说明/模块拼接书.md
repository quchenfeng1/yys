> 本文档展示整个程序从启动到运行的完整模块协作链路，包括模块结构图、启动流程、任务队列搭建、任务执行全链路。帮助开发者理解"所有模块如何拼在一起"。

## 三、任务队列搭建阶段

### 3.1 用户点击"启动"后的完整链路

```
用户点击 UI 的"启动"按钮
  │
  ▼
10-参数桥接模块 → RunBridge
  │  发布 start_requested 事件
  ▼
08-事件通信总线
  │  分发事件给订阅者
  ▼
09-运行控制中心._on_start_requested()
  │
  ├── 1. 允许性检查
  │     ├── 调 15-账号管理模块.get_current() → 获取当前账号
  │     ├── 调 06-配置管理中心.get() → 读取上限配置
  │     ├── 调 01-设备连接模块.is_connected() → 检查连接
  │     └── 全部通过 → 继续
  │
  ├── 2. 初始化连接
  │     └── 调 01-设备连接模块.connect()
  │
  ├── 3. 加载调度状态
  │     └── 调 05-时间调度模块.load_state()
  │
  ├── 4. 初始化空 FIFO 队列
  │
  ├── 5. 状态置为 running
  │     └── 调 07-运行时状态管理.set_state("run_status", "running")
  │
  ├── 6. 启动填充线程 _filler_loop()
  │
  └── 7. 启动执行线程 _executor_loop()
```

### 3.2 填充线程：任务队列搭建

填充线程启动后，立即开始构建任务队列：

```
填充线程 _filler_loop() 启动
  │
  └── 循环（间隔2~3秒）：
        │
        ├── 1. 熔断检查（跳过已熔断）
        │
        ├── 2. 允许性检查（上限/连接）
        │
        ├── 3. 调 05-时间调度模块.get_due_tasks()
        │       │
        │       ├── 扫描所有启用任务
        │       ├── is_due() 双重判据检查
        │       ├── check_times_limit() 次数上限检查
        │       ├── 依赖检查（depends_on）
        │       ├── 调 15-账号管理模块.get_task_scope() 过滤
        │       └── 返回到期任务列表
        │
        ├── 4. 到期任务列表按 priority 降序排列
        │
        ├── 5. 加锁 → 遍历列表
        │     ├── 未入队 → 加入 FIFO 队列尾部 + 加入已入队集合
        │     └── 已在队列 → 跳过
        │
        ├── 6. 解锁
        │
        ├── 7. 更新 queue_length / queue_contents → 07-状态管理
        │
        ├── 8. 发布 schedule_updated 事件 → 08-事件总线
        │       │
        │       └── 11-用户界面模块.TaskQueuePanel 收到事件
        │             → 重建队列卡片展示
        │
        └── 9. 休眠2~3秒 → 回到开头
```

```
┌───────────────────────────────────────────────────┐
│              运行中（running）                       │
│                                                     │
│  填充线程（2~3秒/轮）                                │

## 四、任务执行阶段

### 4.1 单次任务执行全链路

当一个任务从队列头部取出后，经过以下完整链路：

```
执行线程出队 → 任务名如 "yuhun（御魂副本）"
  │
  ├── 1. 从已入队集合移除（允许未来重新入队）
  │
  ├── 2. 熔断检查 + 允许性检查（兜底）
  │
  ├── 3. 发布 task_started 事件
  │     └── 11-UI面板 / 12-日志监控 收到事件
  │
  ├── 4. 构造 TaskContext
  │     ├── task_config    ← 06-配置管理中心.get_task_config("yuhun")
  │     ├── executor       ← 14-执行器模块（已含安全注入）
  │     ├── recognizer     ← 02-图像识别模块
  │     ├── stop_event     ← 09-运行控制中心（停止信号）
  │     └── timeout        ← 300秒（来自配置）
  │
  ├── 5. 创建子线程 → task.execute(context)
  │     │
  │     │  进入 04-任务执行引擎.TaskGraph.run()
  │     │  ┌──────────────────────────────────────┐
  │     │  │ 步骤图执行（御魂副本为例）：            │
  │     │  │                                      │
  │     │  │ 步骤① [边界检查] stop_event? 超时?    │
  │     │  │   → EnterYuhun(特化)                  │
  │     │  │     ├── 识图: 庭院→探索→御魂入口      │
  │     │  │     └── 调 02+03+01 → 14-执行器       │
  │     │  │                                      │
  │     │  │ 步骤② [边界检查] stop_event? 超时?    │
  │     │  │   → CheckStamina(通用)               │
  │     │  │     └── 体力不足→跳过                 │
  │     │  │                                      │
  │     │  │ 步骤③ [边界检查] stop_event? 超时?, 需组队?    │
  │     │  │   → 需组队 → 根据 team_host 选模式                    │
  │     │  │     ├── 模式A(主号带队):                                │
  │     │  │     │  主号 CoopHost → 小号 CoopJoin → 主号 BattleLoop  │
  │     │  │     └── 模式B(小号开车):                                │
  │     │  │      小号 CoopHost → 主号 CoopPassive → 小号 BattleLoop │
  │     │  │   → PreCheckTeam(通用)               │
  │     │  │                                      │
  │     │  │ 步骤④ [边界检查] stop_event? 超时?    │
  │     │  │   → SelectTeam(通用)                 │
  │     │  │                                      │
  │     │  │ 步骤⑤ [边界检查] stop_event? 超时?    │
  │     │  │   → BattleLoop(通用, 循环30次)       │
  │     │  │     ├── 运行时进度检查：读取 task_runtime_progress      │
  │     │  │     ├── 已 completed=30 → 跳过（已做完）              │
  │     │  │     ├── 已 completed=10 → 循环剩余20次               │
  │     │  │     ├── 每完成1次 → completed++ → 更新 07 状态       │
  │     │  │     ├── 等待战斗结束                   │
  │     │  │     ├── 检测胜负                      │
  │     │  │     ├── 结算点击                      │
  │     │  │     └── [步骤内定期] check_interrupt  │
  │     │  │                                      │
  │     │  │ 步骤⑥ [边界检查] stop_event? 超时?    │
  │     │  │   → ClaimReward(通用)                │
  │     │  │                                      │
  │     │  │ 步骤⑦ [边界检查] stop_event? 超时?    │
  │     │  │   → ReturnHall(通用)                 │
  │     │  │                                      │
  │     │  │ → 全部完成 → 返回 TaskResult.success  │
  │     │  └──────────────────────────────────────┘
  │     │
  │     └── 返回 TaskResult
  │
  ├── 6. 判断 TaskResult.status
  │     ├── success → 调 05-时间调度.mark_done(成功)
  │     ├── fail    → 异常恢复 + mark_done(失败)
  │     ├── timeout → 终止子线程 + mark_done(失败)
  │     └── aborted → 直接收尾（用户已点停止）
  │
  ├── 7. 记录执行指标
  │     └── 调 12-日志监控中心.record_task_done()
  │
  └── 8. 更新 queue_length → 取下一個
```

### 4.2 步骤内的执行器调用细节

每个步骤在执行过程中，会通过 `context.executor` 调用 **14-执行器模块**，进而协调三个底层模块：

```
以 BattleLoop 中的"点击挑战按钮"为例：

context.executor.click_image("common/battle/challenge_btn")
  │
  ├── 1. 调 02-图像识别模块.find("challenge_btn")
  │     → 返回 MatchResult(center=(637,598), w=80, h=40, confidence=0.95)
  │
  ├── 2. 未找到 → 返回 False（步骤处理失败情况）
  │
  ├── 3. 调 03-防封策略模块.random_offset_in_bounds(637, 598, 80, 40)
  │     → 返回图标矩形内的安全坐标 (641, 602)
  │
  ├── 4. 调 03-防封策略模块.human_move_path(当前光标, 641, 602)
  │     → 返回贝塞尔曲线路径点列表
  │
  ├── 5. 调 03-防封策略模块.maybe_long_pause()
  │     → 概率触发走神暂停
  │
  ├── 6. 调 01-设备连接模块.click(641, 602)
  │     → 执行 ADB shell input tap 641 602
  │
  ├── 7. 操作计数（由执行线程更新到运行控制中心）
  │
  └── 8. 返回 True
```

### 4.3 场景检测与弹窗拦截

执行循环中集成了场景检测机制，应对误触和弹窗干扰：

**弹窗扫描（每步执行前）**：
```
09-运行控制中心 执行线程
  → 调 14-执行器模块.detect_scene(["popup_reward", "popup_ad", "popup_update", ...])
  → 匹配到弹窗模板名
      → 调 14-执行器模块.click_image("close_btn") 关闭弹窗
      → 重新截图确认弹窗已关闭
      → 继续执行
  → 未匹配（无弹窗）→ 直接执行
```

**场景验证（每步执行后）**：
```
09-运行控制中心 执行线程
  → 调 14-执行器模块.ensure_scene(expected_scene)
  → 确认在预期场景 → 继续下一步
  → 不在预期场景
      → 调 14-执行器模块.detect_scene([候选场景模板列表])
      → 匹配到某场景 → 更新 07.last_known_scene
                      → 走该场景对应的恢复路径
      → 未匹配 → 截图保存 → 递增异常计数 → 失败冷却
```

### 4.4 异常场景恢复（完整链路）

当任务步骤执行失败时，自动进入场景恢复流程：

```
步骤失败（click_image假 / ensure_scene超时 / 抛出异常）
  │
  ├── 1. 截图保存 → 12-日志监控中心.capture_on_error()
  │
  ├── 2. 页面分析 → 14-执行器.detect_scene([庭院,探索,御魂,结算,失败,登录,弹窗...])
  │     │
  │     ├── 匹配到已知场景 → 更新 07.last_known_scene
  │     └── 未匹配 → 进入保护模式
  │
  ├── 3. 恢复路径选择
  │     ┌──────────────────────────────────────┐
  │     │ "战斗结算" → click("确认") → 返回   │
  │     │ "战斗失败" → click("退出") → 回庭院  │
  │     │ "登录界面" → 游戏断开 → 终止任务    │
  │     │ "弹窗"     → click("关闭") → 重试   │
  │     │ "庭院/探索" → 重新导航到目标入口     │
  │     └──────────────────────────────────────┘
  │
  ├── 4. 恢复验证 → ensure_scene(目标场景)
  │     ├── 成功 → 继续执行
  │     └── 失败 → recover_count++
  │           → recover_count >= 3 → 放弃当前任务
  │           → 执行下一个（避免死循环浪费资源）
  │
  └── 5. 保护模式（完全未知）
        ├── 通用退出序列：关弹窗 → 返回键 → 取消 → 回庭院
        ├── 任一成功 → 恢复
        └── 全部失败 → 跳过任务 → 保护资源
```

### 5.1 强制停止链路

```
用户点击 UI 的"停止"按钮

  ▼
10-参数桥接模块 → RunBridge

  ▼
08-事件通信总线
  │  分发事件
  ▼
09-运行控制中心._on_stop_requested()
  │
  ├── 1. 设置 _stop_event（通知所有线程终止）
  │
  ├── 2. 中断填充线程（下一轮循环检测到 stop_event 后退出）
  │
  ├── 3. 中断任务子线程（_current_task_thread 被强制终止）
  │     └── 当前执行中的步骤被中断，返回 TaskResult.aborted
  │
  ├── 4. 保存运行时进度 → 调 07.set_state("task_runtime_progress", ...)
  │     └── 写 task_runtime_progress.json（记录各任务已完成的循环次数）
  │
  ├── 5. 清空 FIFO 队列（_fifo_queue.clear() + _enqueued_set.clear()）
  │
  ├── 6. 执行收尾 _cleanup()
  │     ├── 生成运行摘要 → 调 12-日志监控中心
  │     ├── 保存调度状态 → 调 05-时间调度模块.save_state()
  │     ├── 更新 run_status = stopped → 调 07-状态管理
  │     ├── 断开连接 → 调 01-设备连接模块.disconnect()
  │     └── 发布 run_summary 事件 → 08-事件通信总线
  │           └── 11-UI面板 收到 → 展示运行报告
  │
  └── 7. 状态置为 stopped
```

### 6.2 核心数据流

```
配置数据流：
  06-配置管理中心 ← YAML/JSON 文件
    → 所有模块读取配置

事件数据流：
  任意模块 → 发布事件 → 08-事件通信总线 → 分发给订阅者

状态数据流：
  任意模块 → set_state() → 07-运行时状态管理 → 发布 state_changed
    → UI 订阅 → 自动刷新展示

操作数据流：
  04-任务步骤 → context.executor.click_image()
    → 14-执行器模块 → 02-图像识别(find)
                    → 03-防封策略(random_offset)
                    → 01-设备连接(click)
    → 返回结果给任务步骤

运行时进度数据流：
  04-BattleLoop 每完成1次 → completed++
    → 调 07.set_state("task_runtime_progress", {task: {completed, total}})
    → 用户点击停止 → 09 读取 → 写 task_runtime_progress.json
    → 下次启动 → 09 读 json → 调 07.set_state → 04 读取剩余次数
```

```

  → 10-参数桥接模块.set()

### 6.4 性能优化关键设计

| 优化点 | 说明 | 影响模块 |
|-------|------|---------|
| **截图缓存** | 同一任务步骤内复用截图，避免重复 ADB 请求 | 02-图像识别模块 |
| **识别结果缓存** | 1 秒 TTL，避免轮询时重复模板匹配 | 02-图像识别模块 |
| **点分路径索引缓存** | `get()` 首次遍历后缓存结果，后续 O(1) 读取 | 06-配置管理中心 |
| **批量状态更新** | `set_states()` 合并多次更新为一次 `state_changed` 事件 | 07-运行时状态管理 |
| **事件去重** | 短时间内相同事件自动合并 | 08-事件通信总线 |
| **handler 超时** | 慢 handler 5 秒后自动中断，不阻塞队列 | 08-事件通信总线 |
| **自适应休眠** | 无任务时空闲越久休眠越长（2~10秒），减少 CPU 空转 | 09-运行控制中心 |
| **日志预过滤** | level 低于最低级别时直接丢弃，避免对象创建开销 | 12-日志监控中心 |
| **异步日志写入** | 日志放入队列后立即返回，不阻塞业务线程 | 12-日志监控中心 |
