## 一、用户提出的8模块思路梳理

| # | 模块 | 用户描述的核心职责 |
|---|------|--------------------|
| 1 | **定时模块** | 项目核心。前绑定程序主体触发开关，后绑定单独任务。程序确定某任务打开后，定时模块控制任务在不同时间去/不去执行 |
| 2 | **任务模块** | 拆分为特化模块+通用模块。一个完整任务可仅由一个特化模块构成，也可由多个特化+通用模块联合控制。模块间为先后或判断关系：前一个输出值，据此判断走战斗通用模块、中间任务模块还是返回大厅的错误模块 |
| 3 | **传参模块** | 决定一个体系全部参数的模块。如某任务需先设定时任务、再设战斗前御魂配置等，这些外部传入参数也可分模块（共通配置复用）。负责构建UI和程序之间的桥梁 |
| 4 | **UI模块** | 分解为日志、菜单、任务配置、任务列表等子模块。与传参模块链接：运行按钮链接运行传参模块传入启停信号；时间配置区域链接时间传参模块控制某任务配置文件 |
| 5 | **配置模块** | 控制某任务的全部参数，程序启停等均需查看配置模块是否允许 |
| 6 | **识图控制模块** | 集成在每个需识图的任务中，受安全模块控制，防止连续乱点导致封号 |
| 7 | **安全模块** | 控制识图模块以控制其安全性 |
| 8 | **连接模块** | 控制模拟器连接等，连接错误从此处抛出 |

此外：程序骨架（程序结构）、图片存放目录等作为基础设施。

## 二、可行性总体评价

**结论：整体思路优秀且可行，方向正确。**

### 亮点（应保留的设计）

1. **任务=特化模块+通用模块组合** ★★★
   - 这是**组合模式（Composite Pattern）**的精髓。一个御魂副本 = [进入御魂界面(特化)] + [选层数(特化)] + [阵容检查(通用)] + [战斗循环(通用)] + [结算领奖(通用)] + [返回庭院(通用)]。
   - 通用模块（战斗、结算、返回）可被所有副本复用，特化模块只写该副本独有的界面操作。
   - 新增副本时只需写几个特化模块，通用部分零成本复用。这正是说明书v1.7"任务插件化"理念的进一步深化。

2. **模块间"先后或判断关系，前一个输出值判断走哪条路"** ★★★
   - 这是**管道/责任链模式（Pipeline / Chain of Responsibility）**与**状态机**的结合。
   - 每个模块执行后输出结果（成功/失败/场景标识），调度据此决定下一步：走战斗模块、走错误恢复模块（返回大厅）、还是走中间模块（换御魂）。
   - 天然支持错误恢复——识别失败不崩溃，而是走"返回大厅→跳过任务"分支。

3. **传参模块作为UI和程序的桥梁** ★★
   - 这是**数据绑定（Data Binding）/MVVM**思想的体现。UI不直接操作程序逻辑，而是通过参数模型间接控制，实现UI与逻辑解耦。

4. **安全模块独立于识图模块** ★★
   - 这是**策略注入（Strategy Injection）**模式。安全策略不硬编码在识图里，而是作为独立模块注入，便于调整防封号强度而不改识图代码。

### 需要改进的点（详见第三节）

| 问题 | 涉及模块 | 严重程度 |
|------|----------|----------|
| "定时模块前绑定触发开关"混淆了调度与运行控制 | 定时模块 | 中 |
| "传参模块"实际包含两个不同层次（配置模型+UI绑定），应拆分 | 传参模块 | 中 |
| "安全模块控制识图模块"范围不够，安全应覆盖识图+点击+滑动+等待全链路 | 安全/识图 | 中 |
| 缺少模块间通信机制（事件总线），直接互调会紧耦合 | 全局 | 高 |
| 缺少全局状态管理（当前账号/连接状态/场景/运行态） | 全局 | 高 |
| 任务模块"先后关系"建议升级为"任务步骤图（DAG）"，支持条件分支与循环 | 任务模块 | 中 |

## 三、逐模块分析与改进建议

### 3.1 定时模块

**用户思路**：前绑定触发开关，后绑定任务，控制任务在不同时间去/不去执行。

**分析**：
- ✅ "控制任务何时执行"的调度职责定位准确，对应说明书的 Scheduler（5.9）。
- ⚠️ "前绑定触发开关"——触发开关（启动/停止/暂停按钮）本质是**运行控制**，与"何时执行哪个任务"的**时间调度**是两个不同职责。把它们放在一个模块里会导致：暂停时调度逻辑被阻塞、启动时调度器需要感知UI状态。
- 💡 **建议**：将"触发开关"拆出为独立的**运行控制模块**（RunController），定时模块只专注于"时间规则→next_run_time→日程表→取下一个到期任务"的纯调度逻辑。运行控制模块负责接收UI启停信号，控制调度循环的运行/暂停/停止。

### 3.2 任务模块

**用户思路**：特化+通用组合，模块间先后或判断关系，前一个输出值判断走哪条路。

**分析**：
- ✅ 特化/通用分离与组合的设计非常优秀，强烈建议保留。
- ✅ "前一个输出值判断走哪条路"的分支逻辑正确，是错误恢复的关键。
- ⚠️ 简单的"先后关系"不足以表达所有场景。例如：御魂副本中"战斗循环"需要重复N次（循环）；真蛇副本有多个阶段，每阶段阵容不同（阶段切换）；组队副本需要等待队友（并行等待）。
- 💡 **建议**：将任务模块内部结构升级为**任务步骤图**：
  - 引入 `TaskStep`（任务步骤）概念，每个步骤是一个特化或通用模块。
  - 步骤间关系用**有向图**描述，支持：顺序、条件分支、循环、跳转。
  - 每个步骤执行后返回 `StepResult`（success/fail/skip/scene_id），步骤图据此决定下一节点。
  - 这比线性"先后关系"更强大，且仍然兼容简单场景（线性图=先后关系）。

```
任务步骤图示例（御魂副本）：
  enter_dungeon(特化) →pre_check_team(通用) → select_floor(特化) → select_team(通用)
      → [条件] lock_team(通用) → battle_loop(通用,循环N次) → settle(通用) → return_hall(通用)
                                              ↓失败
                                         error_return(通用,返回大厅)
```

### 3.3 传参模块

**用户思路**：决定一个体系全部参数，构建UI和程序之间的桥梁。

**分析**：
- ✅ "UI和程序之间的桥梁"定位正确。
- ⚠️ "传参模块"实际混合了两个不同关注点：
  1. **配置数据模型**（Config Model）：描述"一个任务需要哪些参数"（如御魂任务需要team_id、times、floor、repeat规则）。这是静态的数据结构定义。
  2. **UI数据绑定**（UI Binding）：UI控件与配置数据的双向同步（UI改了→配置改了→程序读到新值；程序状态变了→UI显示更新）。这是动态的绑定机制。
- 💡 **建议**：拆分为两个子模块，但归入"传参模块"这一个大的桥梁层：
  - **配置数据模型层**：定义每个任务的参数schema，与配置模块（#5）协作读写。
  - **UI数据绑定层**：实现Qt信号槽绑定，UI控件变化→更新配置模型→通知程序。
  - 这样"传参模块"仍然是一个整体概念，但内部职责清晰。

### 3.4 UI模块

**用户思路**：分解为日志、菜单、任务配置、任务列表等，与传参模块链接。

**分析**：
- ✅ UI子模块划分合理。日志、菜单、任务配置、任务列表是四个自然的切分维度。
- ✅ "运行按钮链接运行传参模块"的思路正确——UI只发信号，不直接操作逻辑。
- 💡 **建议补充**：增加一个**状态展示子模块**，负责展示全局运行状态（当前账号、连接状态、当前执行任务、进度条、倒计时）。这些信息横跨多个模块，需要单独的区域展示。

### 3.5 配置模块

**用户思路**：控制某任务全部参数，程序启停等均需查看配置模块是否允许。

**分析**：
- ✅ 作为配置中心的设计正确，对应说明书的 ConfigManager（5.5）。
- ⚠️ "程序启停需查看配置模块是否允许"——启停的"允许性检查"（如防封号上限、运行时段）应归运行控制模块，配置模块只提供参数。否则配置模块会侵入运行逻辑。
- 💡 **建议**：配置模块只负责**数据的读写与校验**（加载YAML/JSON、提供get/set接口、持久化），不负责"是否允许运行"的判断。运行允许性判断放运行控制模块。

### 3.6 识图控制模块

**用户思路**：集成在每个需识图的任务中，受安全模块控制。

**分析**：
- ✅ "集成在每个任务中"——识图作为任务的工具被调用，定位正确。
- ⚠️ "受安全模块控制"——安全模块不应"控制"识图（那样识图变成被动的），而应"注入策略"（识图主动调用安全模块获取随机参数）。
- 💡 **建议**：识图模块提供纯识别能力（find/exists/wait），安全策略通过**执行模块（Executor）**注入。即：任务调用Executor→Executor调识图获取坐标→Executor调安全模块加随机偏移→Executor执行点击。识图本身不做安全处理，保持纯粹。这样识图模块可独立测试，安全策略可独立调整。

### 3.7 安全模块

**用户思路**：控制识图模块以控制其安全性。

**分析**：
- ⚠️ 范围不够。安全不仅关乎识图/点击，还涉及：滑动（随机时长）、等待（随机延迟）、长操作间隔（走神暂停）、每日运行上限。
- 💡 **建议**：安全模块升级为**防封号策略引擎**，覆盖全操作链路：
  - 点击：随机偏移、贝塞尔轨迹
  - 滑动：随机时长、随机起止点微调
  - 等待：随机延迟抖动
  - 节奏：走神暂停概率触发
  - 上限：每日运行时长/操作次数检查
  - 所有需要"拟人化"的操作都从这里获取参数。

### 3.8 连接模块

**用户思路**：控制模拟器连接，连接错误从此处抛出。

**分析**：
- ✅ 定位准确，对应说明书的 ADBClient（5.1）+ EmulatorManager。
- ✅ "连接错误从此处抛出"——统一异常出口的设计正确。
- 💡 **建议补充**：连接模块还应负责**连接状态监控**（心跳检测断线）和**自动重连**（断线后尝试恢复），并通过事件总线通知其他模块连接状态变化。

## 五、新增模块的必要性说明

### 5.1 为什么需要"状态管理模块"？

**问题**：脚本运行中有大量全局状态需要被多个模块共享：
- 当前操作账号（主号/小号1/小号2）
- 当前连接的模拟器设备ID
- 当前游戏场景（庭院/战斗中/探索中）
- 运行状态（运行中/暂停/停止/错误恢复）
- 今日已运行时长/操作次数

如果这些状态散落在各模块内部，会导致模块间互相查询状态时紧耦合，且状态不一致风险高。

**方案**：集中到 `StateManager`，所有模块通过它读写全局状态，状态变化通过事件总线广播。

### 5.2 为什么需要"事件总线模块"？

**问题**：模块间如果直接互相调用，会形成网状依赖：
- 连接断开 → 需通知定时模块暂停、通知UI标红、通知任务模块中止
- 任务完成 → 需通知UI更新状态、通知定时模块推进next_run_time、通知日志记录
- 用户点停止 → 需通知运行控制、通知定时、通知当前任务

直接调用意味着每个模块都要持有其他模块的引用，且调用顺序硬编码。

**方案**：引入 `EventBus`，模块只发事件（publish）和订阅事件（subscribe），不直接持有对方引用。
- `connection_lost` 事件 → 定时模块订阅（暂停）、UI订阅（标红）、任务订阅（中止）
- `task_done` 事件 → UI订阅（更新）、定时订阅（推进）、日志订阅（记录）
- 实现真正的发布-订阅解耦。

### 5.3 为什么需要"运行控制模块"？

**问题**：用户把"触发开关"放在定时模块里。但启停控制涉及：
- 接收UI的启动/停止/暂停信号
- 检查运行允许性（防封号上限、配置允许）
- 控制调度循环的生命周期（运行/暂停恢复/优雅停止）
- 协调多模块响应（停止时需通知当前任务收尾、保存状态、断开连接）

这些是**运行生命周期管理**，与"何时执行哪个任务"的**时间调度**是正交的两个职责。混在一起会让定时模块既管时间又管生命周期，职责膨胀。

**方案**：独立 `RunController`，专注运行生命周期。定时模块只管"给定了运行态，下一个该执行什么任务"。

### 5.4 为什么需要"日志与监控模块"？

**问题**：现有 `core/logger.py` 只是简单的文本日志输出，缺少：
- **结构化记录**：日志只有文本，无法按模块/任务/步骤筛选检索
- **运行指标**：不知道每个任务执行了多少次、成功率多少、平均耗时多少
- **异常截图**：出错时没有自动保存现场截图，事后无法排查
- **运行报告**：缺少每日/每周总结，不知道脚本整体运行情况
- **日志事件化**：UI日志面板需要实时获取日志，目前靠轮询或直接耦合

如果这些能力散落在各模块中实现，会导致日志逻辑侵入业务代码，且各模块日志格式不一致。

**方案**：独立 `Monitor` 模块（日志与监控），统一负责：
- 结构化日志记录（带模块/级别/任务/步骤/时间戳/标签）
- 运行指标收集与统计（执行次数/成功率/耗时）
- 异常自动截图归档（出错时截图+上下文保存）
- 运行报告生成（每日/每周总结）
- 日志事件化（通过事件总线发布，UI日志面板订阅）

详见 `12-日志与监控模块.md`。

```
              │  │ 结构化日志    │  │    │ +配置迁移     │
              │  │ 运行指标/截图  │  │    └──────────────┘
              │  └──────┬───────┘  │
              │         │          │
              │  ┌──────▼───────┐  │
              │  │  定时模块     │  │

```

**依赖原则**：
- 核心层（识图/安全/连接/任务/定时）之间通过事件总线通信，不直接持有引用。
- 支撑层（配置/状态/事件/运行控制）被核心层依赖，但不反向依赖。
- 桥梁层（传参/UI）只与支撑层交互，不直接碰核心层。

## 十、进一步优化方案（v2.0新增）

在用户确认6项核心优化后，基于"进一步提出优化"的要求，对各模块提出以下增强：

### 10.1 新增：日志与监控模块（第12个模块）

| 增强点 | 说明 |
|--------|------|
| 结构化日志 | 日志带模块/级别/任务/步骤/时间戳/标签，可按维度筛选 |
| 运行指标 | 自动统计各任务执行次数/成功率/平均耗时/总耗时 |
| 异常截图 | 出错时自动截图+保存上下文（当前任务/步骤/配置），便于排查 |
| 运行报告 | 每日/每周自动生成运行总结（执行了什么、成功几次、失败几次） |
| 日志事件化 | 日志通过事件总线发布，UI日志面板订阅显示，不直接耦合 |

### 10.2 任务模块增强

| 增强点 | 说明 |
|--------|------|
| 步骤超时 | 每个 TaskStep 可配 timeout，超时自动转 fail，避免卡死 |
| 步骤重试 | 可配 retry_count，失败自动重试，重试间隔由安全模块控制 |
| 步骤回滚 | 失败时执行可选的 cleanup 回调（如关闭已打开的弹窗） |
| 中断检查点 | 步骤执行中定期检查 stop 信号，支持优雅中断（不等待整个步骤完成） |
| 步骤并行 | 支持 parallel 节点，多个无依赖步骤可并行执行（如等待+检测） |

### 10.3 事件总线增强

| 增强点 | 说明 |
|--------|------|
| 事件溯源 | 可选记录全部事件历史，支持调试时回放事件序列排查问题 |
| 事件优先级 | 系统级事件（connection_lost/run_limit_reached）高优先级插队处理 |
| 事件去重 | 短时间内重复事件自动合并，防止事件风暴（如连续多次connection_lost） |

### 10.4 配置模块增强

| 增强点 | 说明 |
|--------|------|
| 三级分层覆盖 | global → account → task，后者覆盖前者，支持"全局默认+账号定制+任务微调" |
| 配置迁移 | 配置文件带版本号，升级时自动迁移旧配置格式，兼容历史版本 |
| 配置导入导出 | 支持将全套配置导出为zip备份，或从备份恢复 |

### 10.5 安全模块增强

| 增强点 | 说明 |
|--------|------|
| 操作审计日志 | 记录每次操作的坐标/时间/类型/截图，便于事后分析和行为审计 |
| 行为指纹多样性 | 长时间运行时逐渐变化行为参数（偏移半径/延迟抖动范围），避免行为模式固化被检测 |

### 10.6 运行控制增强

| 增强点 | 说明 |
|--------|------|
| 异常恢复策略 | 连接断开→暂停重连；识图失败→重试N次；任务异常→返回大厅后继续调度 |
| 熔断机制 | 连续失败超过阈值（如5次）时自动停止，避免死循环浪费操作次数 |

### 10.7 连接模块增强

| 增强点 | 说明 |
|--------|------|
| 连接质量监控 | 记录截图延迟、命令响应时间，质量差时通过事件总线告警 |
| 连接池预热 | 多开场景下提前建立连接，账号切换时无需等待 |

> 以上增强已写入各模块文件的"六、进一步增强（v2.0）"段落。实现时按优先级逐步落地，不要求一次全部实现。
