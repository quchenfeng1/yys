# 04-任务执行引擎（Task Execution Engine）

> **类型**：核心运行层  ｜  **对应说明书**：BaseTask 9.1 + DungeonTask 6.4  ｜  **对应用户模块**：#2 任务模块

---

## 一、目的与作用

**一句话定位**：将任务拆解为"特化模块+通用模块"的组合，通过任务步骤图（DAG）描述执行流程，支持顺序/条件分支/循环/错误恢复。

**核心职责**：
1. **任务步骤化**：每个任务由多个步骤组成，步骤分特化（副本独有）和通用（全项目复用）
2. **步骤图引擎**：用有向图描述步骤间关系，支持顺序/分支/循环/跳转
3. **错误恢复**：步骤失败时自动走错误恢复分支（返回大厅→跳过任务），不崩溃
4. **可中断执行**：步骤边界检查停止信号，响应外部中断请求
5. **自动注册**：任务文件放入 tasks/ 目录即自动发现注册，无需改代码

**设计原则**：
- **组合优于继承**：任务不是一个大类，而是多个步骤的组合
- **通用模块复用**：战斗循环、结算领奖、返回庭院等步骤全项目共享
- **特化模块最小化**：每个副本只写自己独有的界面操作
- **步骤图声明式**：执行流程用图描述，而非代码里的 if/for 嵌套
- **步骤边界可中断**：步骤内部原子执行不中断，但步骤间检查停止信号，快速响应停止/超时

## 三、运行逻辑

### 3.1 步骤图执行流程

步骤图引擎在**步骤边界**检查停止信号，步骤内部保持原子执行：

```
步骤图开始执行（接收到 context，含 stop_event 和 timeout）
  → 记录任务开始时间
  → 从入口步骤开始循环：

  步骤循环开始：
    ├── [步骤边界] 检查 stop_event 是否被设置
    │   ├── 已设置 → 走中断收尾 → 返回 TaskResult(status="aborted")
    │   └── 未设置 → 继续
    ├── [步骤边界] 检查是否超时（当前时间 - 开始时间 > timeout）
    │   ├── 已超时 → 走中断收尾 → 返回 TaskResult(status="timeout")
    │   └── 未超时 → 继续
    ├── 执行当前步骤的 execute(context)
    ├── 发布 step_done 事件（含步骤名和结果）
    ├── 判断结果：
    │   成功 → 按默认边进入下一步 或 按 next_step 跳转
    │   失败 → 走 error 恢复分支
    │   跳过 → 按条件边跳到指定步骤
    │   重试 → 重新执行当前步骤
    └── 回到步骤循环开始

  → 所有步骤完成 → 返回 TaskResult(status="success")
```

### 3.2 步骤分类

**通用模块**（全项目复用）：

| 通用模块 | 功能 | 复用场景 |
|----------|------|----------|
| BattleLoop | 战斗循环：等待结束→检测胜负→结算；支持运行时进度恢复（从 `task_runtime_progress` 读取剩余次数） | 所有有战斗的副本 |
| ClaimReward | 领取奖励：点击结算→确认→关弹窗 | 所有副本结算后 |
| ReturnHall | 返回庭院：点返回→确认退出→等加载 | 所有任务收尾 |
| PreCheckTeam | 阵容检查：验证当前阵容→不匹配则修正 | 所有战斗任务进战前 |
| SelectTeam | 选阵容：界面→选中→锁定 | 所有战斗任务进战时 |
| ErrorReturn | 错误恢复：识别失败→返回大厅→标记跳过 | 所有任务的错误分支 |
| CheckStamina | 体力检查：体力不足则跳过 | 所有消耗体力的副本 |
| ClosePopup | 关弹窗：检测并关闭通用弹窗 | 任意步骤间 |
| **CoopHost** | **组队主机**：创建队伍→邀请→等待加入→开战（谁开队谁执行） | 需要组队的战斗副本 |
| **CoopJoin** | **组队成员**：接收邀请→加入队伍→准备就绪 | 需要组队的战斗副本 |
| **CoopPassive** | **组队待机**：加入队伍后不操作，等待战斗结束自动领奖（模式B：小号开车时主号用） | 被带的一方 |
| **FragmentExchange** | **碎片交换**：进入好友界面→发起/接受碎片请求→确认 | 碎片交换任务 |

**特化模块**（副本独有）：每个副本只编写特有的入口操作，如进入副本、选择层数等。

### 3.3 任务组合示例

```
御魂副本任务 = EnterYuhun(特化) → CheckStamina(通用) → PreCheckTeam(通用)
             → SelectTeam(通用) → BattleLoop(通用, 循环N次)
             → ClaimReward(通用) → ReturnHall(通用)
             [任何步骤失败] → ErrorReturn(通用)
             [中断恢复] BattleLoop 从 task_runtime_progress 读取剩余次数

每日签到任务 = SignInEntry(特化) → ClaimReward(通用) → ReturnHall(通用)
             [失败] → ErrorReturn(通用)
```

> **运行时进度恢复**：当任务因用户停止或异常中断后重新启动时，BattleLoop 检查 `task_runtime_progress` 中该任务的 `completed` 值，从剩余次数开始执行。任务配置文件中的 `loop_count` 不变，进度独立存储于 `07-运行时状态管理` 的 `task_runtime_progress` 键中。

### 3.4 中断与超时机制（与运行控制中心的協作）

任务执行引擎通过 TaskContext 接收来自运行控制中心的停止信号和超时设定，在步骤边界做出响应：

**停止响应流程**：
```
运行控制中心用户点击停止
  → 设置 context.stop_event
  → 步骤图引擎在当前步骤完成后检查到 stop_event
  → 停止执行后续步骤，跳过剩余步骤
  → 执行收尾（如返回庭院）
  → 返回 TaskResult(status="aborted")
```

**超时响应流程**：
```
运行控制中心执行线程创建任务子线程时设定超时（如300秒）
  → context.timeout = 300
  → 步骤图引擎每执行完一个步骤检查耗时
  → 超时 → 停止执行后续步骤
  → 返回 TaskResult(status="timeout")
```

**关键规则**：
- **步骤内不中断**：正在执行的步骤（如等待战斗结果）不受 stop_event 影响，保持原子性
- **步骤边界响应**：stop_event 和超时检查在每一步执行前和执行后进行
- **收尾保障**：即使被中断，也会执行 ErrorReturn 等清理步骤

## 四、重点功能

### 4.1 步骤图引擎

用有向图描述任务流程，支持顺序执行、条件分支、循环、任意跳转。步骤执行结果决定下一步走向，失败自动走错误恢复路径，避免任务崩溃。

### 4.2 通用模块复用体系

将战斗、领奖、返回等高频操作抽象为通用模块，所有任务共享。新增副本时只需编写特化入口步骤，其余步骤从通用模块库中组合。

### 4.3 自动注册机制

任务文件放入 tasks/ 对应分类目录即被自动发现注册，无需手动维护任务列表。支持 daily / permanent / event / special 四类任务分类。

### 4.4 步骤级状态推送

每执行完一个步骤即通过事件总线发布进度事件，UI 可实时展示当前执行到哪一步。

### 4.5 步骤边界可中断

每个步骤原子执行不中断，但步骤间检查停止信号和超时。兼顾了**步骤完整性**（不会出现半执行的步骤）和**快速响应**（用户点停止后最多等待一个步骤的完成时间）。

### 4.6 统一任务结果（TaskResult）

`task.execute()` 返回统一的 TaskResult，包含 status（success/fail/timeout/aborted）和 reason。运行控制中心据此决定如何推进调度或恢复。

### 5.4 核心流程

**任务执行链路（被运行控制中心调用）**：
```
运行控制中心执行线程
  → 构造 TaskContext（stop_event + timeout + executor + ...）
  → 调用 task.execute(context)
     → BaseTask.execute()
        → self._build_graph() → 获取子类定义的 TaskGraph
        → graph.run(context)
           → 步骤循环（每步前检查中断）
           → 返回 TaskResult
     ← 返回 TaskResult
  → 根据 TaskResult.status 决定后续
```

**_execute_step 内部逻辑**：
```
传入步骤和 context
  → 根据 step.retry_count 确定重试次数
  → 循环执行：
      调用 step.execute(context)
      成功 → 返回 StepResult
      失败 → 未达重试上限 → 等待 + 重试
      失败 → 已达重试上限 → 返回 fail
  → 步骤执行异常 → 调用 step.cleanup(context) → 重新抛出
```

### 5.5 关键设计

- **步骤边界可中断**：步骤内部原子执行不中断，步骤间检查 stop_event 和超时
- **TaskResult 统一返回值**：运行控制中心根据 status 决定如何推进调度
- **步骤原子性**：保证每个步骤要么完整执行完，要么完全不执行（不会半截中断）

## 六、使用方法（模块间交互）

### 6.1 外部提供的调用接口

| 调用接口 | 调用方 | 说明 |
|---------|--------|------|
| `task.execute(context) -> TaskResult` | **09-运行控制中心（执行线程）** | 执行整个任务，返回 success/fail/timeout/aborted |
