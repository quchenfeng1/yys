# 09-运行控制中心（Run Control Center）

> **类型**：支撑服务层  ｜  **对应说明书**：5.9 ｜  **说明**：从定时模块拆出，独立管理运行生命周期

---

## 一、目的与作用

**一句话定位**：程序运行生命周期管理。接收UI启停信号，采用**双线程队列驱动架构**：队列填充线程持续将到期任务按优先级入队，任务执行线程从 FIFO 队列取出任务执行。

**与定时模块的职责拆分**：
- **定时模块**：纯调度——回答"哪些任务已到期"
- **运行控制中心**：生命周期——接收信号、维护任务队列、驱动执行、协调收尾

**核心职责**：
1. **信号接收**：通过事件总线订阅 UI 的 start/stop/pause 信号
2. **FIFO 任务队列管理**：维护一个先进先出的待执行任务队列
3. **队列填充（后台线程）**：持续检查定时模块的到期任务，按优先级排序后推入队列
4. **任务执行（主线程）**：从队列头部取出任务并执行
5. **允许性检查**：每轮执行前检查防封号上限、连接状态
6. **停止控制**：强制停止立即中断，优雅停止等步骤完成
7. **暂停恢复**：暂停时保留队列和上下文，恢复后继续
8. **异常恢复**：按异常类型执行重试/重连/跳过/停止策略
9. **熔断保护**：连续失败超阈值时自动熔断
10. **收尾保障**：运行结束时生成摘要、保存状态、断开连接

**设计原则**：
- **队列驱动**：任务通过 FIFO 队列传递，填充和执行解耦到两个线程
- **状态机驱动**：状态转换明确可控
- **停止即终止**：用户停止操作立即生效，不等当前步骤
- **任务线程隔离**：每个任务在独立线程执行，便于精确终止
- **收尾保障**：无论正常停止还是异常退出，统一执行收尾流程
- **上限可控**：统一管理每日运行时长和操作次数上限，到限自动停止

## 三、运行逻辑

### 3.1 架构总览：双线程队列驱动

运行控制中心内部运行两个协作线程，通过 FIFO 任务队列解耦：

```
┌──────────────────────────────────────────────────────────────┐
│                    运行控制中心（running态）                    │
│                                                               │
│  队列填充线程（后台持续运行，间隔2~3秒）                        │
│  ┌────────────────────────────────────────────────────┐      │
│  │ while running:                                     │      │
│  │   ① 熔断检查 + 允许性检查                          │      │
│  │   ② get_due_tasks() → 到期任务列表                 │      │
│  │   ③ 按 priority 降序排序（同优先级按查到顺序）       │      │
│  │   ④ 加锁                                          │      │
│  │   ⑤ 遍历列表，未入队的 → 加入 FIFO 队列尾部         │      │
│  │   ⑥ 记录到已入队集合（去重依据）                    │      │
│  │   ⑦ 解锁                                          │      │
│  │   ⑧ 更新 queue_length / queue_contents             │      │
│  │   ⑨ 发布 schedule_updated 事件                    │      │
│  │   ⑩ sleep(2~3秒)                                  │      │
│  └────────────────────────────────────────────────────┘      │
│                           │                                    │
│                           ▼                                    │
│            ┌─────────────────────────┐                        │
│            │    FIFO 任务队列          │                        │
│            │  [最先到期] → ... → [最后] │  ← 先进先出          │
│            │  已入队集合: {task_a, ...} │  ← 快速去重          │
│            └─────────────────────────┘                        │
│                           │                                    │
│                           ▼                                    │
│  任务执行线程（串行执行，一次一个）                               │
│  ┌────────────────────────────────────────────────────┐      │
│  │ while running:                                     │      │
│  │   ① 加锁 → 从队列头部取出一个任务 → 解锁           │      │
│  │   ② 队列空 → wait(1秒) → 回到①                    │      │
│  │   ③ 从已入队集合中移除该任务                        │      │
│  │   ④ 熔断检查（兜底）                               │      │
│  │   ⑤ 允许性检查（上限/连接，兜底）                   │      │
│  │   ⑥ 发布 task_started 事件                         │      │
│  │   ⑦ 构造 TaskContext（含 stop_event + timeout）    │      │
│  │   ⑧ 创建任务子线程 → task.execute(context)          │      │
│  │      ├ TaskResult.success → mark_done(True)        │      │
│  │      ├ TaskResult.fail → 恢复策略 + mark_done(False)│      │
│  │      ├ TaskResult.timeout → 终止 + mark_done(False)│      │
│  │      └ TaskResult.aborted → 直接收尾               │      │
│  │   ⑨ 记录指标（耗时/成功/失败/熔断计数）             │      │
│  │   ⑩ 更新 queue_length / queue_contents             │      │
│  │   ⑪ 回到①                                        │      │
│  └────────────────────────────────────────────────────┘      │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 状态机

运行控制中心采用四态状态机管理运行生命周期：

```
stopped ──[start信号+允许性检查通过]──► running ──[熔断/致命异常]──► error
   ▲                                        │                        │
   │                           [pause信号]  │  [resume信号]          │
   │                                        ▼                        │
   │                                    paused                       │
   │                                                       [stop信号] │
   └──────────────[stop信号 强制终止]───────────────────────────────┘
```

| 状态 | 说明 | 可转换至 |
|------|------|---------|
| **stopped** | 初始/停止态，无任何运行活动 | running |
| **running** | 运行中，两个线程均在运行 | paused、stopped、error |
| **paused** | 已暂停，队列保留当前内容，两个线程休眠 | running、stopped |
| **error** | 异常态，熔断或致命错误触发 | stopped |

### 3.3 队列填充逻辑（填充线程）

填充线程在 running 态下持续运行（间隔2~3秒）：

```
1. 熔断检查 → 已熔断则休眠等待恢复，本轮不填充
2. 允许性检查 → 上限/连接，不满足则停止填充（等待执行线程收尾）
3. 调用 scheduler.get_due_tasks() → 获取当前所有到期任务列表
   （内部自动：is_due + check_times_limit + 依赖检查过滤）
4. 按 priority 降序排列（同优先级按 get_due_tasks() 返回顺序）
5. 加锁（保护队列和已入队集合的并发访问）
6. 遍历排序后列表，逐个判断：
   → 任务名不在"已入队集合"中 → 加入 FIFO 队列尾部 + 加入已入队集合
   → 任务名已在集合中 → 跳过（已在队列中等待执行）
7. 解锁
8. 更新 queue_length（队列长度）和 queue_contents（任务名列表）到状态管理
9. 发布 schedule_updated 事件（通知 UI 刷新队列展示）
10. sleep(2~3秒)，回到步骤1
```

**关键规则**：
- **无条件持续填充**：不管队列状态如何，每轮都完整检查所有任务，确保新到期任务及时入队
- **双重去重**：通过"已入队集合"确保同一任务不会同时出现在队列中两次
- **入队前预检**：熔断和上限检查在填充线程就做一遍，避免把任务填进去再被执行线程拒掉
- **同优先级顺序**：优先级相同时，按 get_due_tasks() 查到的先后顺序入队（即计算机输出顺序）

### 3.4 任务执行逻辑（执行线程）

执行线程串行执行任务，一次只处理一个，确保执行顺序与队列顺序一致：

```
1. 加锁 → 从 FIFO 队列头部取出一个任务（出队）→ 解锁
2. 队列为空 → wait(1秒) → 回到步骤1（避免忙等CPU空转）
3. 从"已入队集合"中移除该任务（允许未来重新入队）
4. 熔断检查（兜底）→ 熔断则进入 error 态，清空队列
5. 允许性检查（兜底）→ 上限/连接不满足则优雅停止
6. 发布 task_started 事件（通知 UI 和日志）
7. 构造 TaskContext（注入 stop_event + timeout）
8. 创建任务子线程执行（带超时保护）：
   ┌─────────────────────────────────────────────┐
   │ 创建子线程 → task.execute(context)           │
   │ 等待子线程完成（带超时，如 timeout+10秒兜底）  │
   │                                              │
   │ 返回 TaskResult(status="success")            │
   │   → 调 scheduler.mark_done(成功)             │
   │                                              │
   │ 返回 TaskResult(status="fail")               │
   │   → 按异常类型走恢复策略                      │
   │   → 调 scheduler.mark_done(失败)             │
   │                                              │
   │ 返回 TaskResult(status="timeout")            │
   │   → 强制终止子线程                           │
   │   → 记录超时日志                             │
   │   → 调 scheduler.mark_done(失败)             │
   │                                              │
   │ 返回 TaskResult(status="aborted")            │
   │   → 用户已点停止，不推进调度                  │
   │   → 直接进入收尾流程                         │
   │                                              │
   │ 执行中异常抛出 → 捕获异常                    │
   │   → 调 scheduler.mark_done(失败)             │
   │   → 记录错误日志+保存截图                    │
   └─────────────────────────────────────────────┘
8. 记录执行指标（任务名/耗时/成功/失败/熔断计数）
9. 更新 queue_length 到状态管理
10. 回到步骤1
```

**关键规则**：
- **串行执行**：一次只执行一个任务，执行完才取下一個，保证先进先出
- **子线程超时**：每个任务在独立子线程执行，超过超时时间（默认300秒）强制终止，避免单个任务卡死整个调度
- **双重检查**：填充线程入队前检查一次，执行线程出队后检查一次，双重保险
- **出队即移除**：任务出队后立即从已入队集合移除，允许填充线程在重试场景下重新入队

### 3.5 停止策略

| 模式 | 触发方式 | 行为 | 适用场景 |
|------|---------|------|---------|
| **强制停止** | 用户点击停止按钮 | 立即中断填充线程和执行线程，清空队列，直接收尾 | 用户主动停止、紧急情况 |
| **优雅停止** | 内部触发（上限到达/任务完成） | 标记停止请求，等当前步骤完成后清空队列再收尾 | 每日上限到达、全部任务完成 |

### 3.6 暂停/恢复

| 操作 | 填充线程行为 | 执行线程行为 | 队列状态 |
|------|------------|------------|---------|
| **暂停** | 完成本轮填充后休眠，不再检查到期任务 | 等待当前任务子线程完成后休眠，不再取新任务 | 完整保留，不清空 |
| **恢复** | 从休眠中唤醒，继续下一轮填充循环 | 从休眠中唤醒，继续从队列头部取任务 | 内容不变，继续使用 |
| **暂停中停止** | 直接终止（无需唤醒） | 直接终止，当前任务子线程一并终止 | 清空队列 |

**暂停要点**：
- 暂停时如果执行线程正在执行任务（子线程运行中），**等待该任务完成**后才真正进入暂停态
- 暂停期间 UI 仍可查看队列内容（未执行的任务保留在队列中）
- 恢复后填充线程的第一轮检查可能会发现暂停期间新到期的任务，一次性补入队列

### 3.7 异常恢复策略

执行线程捕获到 TaskResult 或异常后，按以下流程恢复：

**连接断开**：
1. 暂停填充线程和执行线程
2. 调用连接模块的退避重连（1s→2s→4s→8s→16s，最多5次）
3. 成功 → 恢复填充和执行线程
4. 失败 → 执行收尾流程

**识图失败**：
1. 记录失败日志
2. 间隔随机延迟后重试（最多3次）
3. 任意一次成功 → 继续执行
4. 3次均失败 → 调用 ErrorReturn 返回大厅 → 跳过该任务

**操作超时**：
1. 记录超时日志
2. 等待后重试（最多2次）
3. 仍超时 → 标记任务失败 → 从队列取下一個

**任务执行异常**：
1. 记录异常日志+自动截取现场截图
2. 调用 ErrorReturn 返回庭院
3. 标记任务失败，不推进 next_run_time
4. 继续下一轮调度

**未知错误**：
1. 自动截取异常现场截图
2. 保存调用栈上下文到 `logs/snapshots/`
3. 执行收尾流程
4. 状态置为 error

### 3.8 熔断保护机制

连续失败超过阈值时触发熔断，避免死循环浪费操作次数：

- **触发阈值**：默认连续失败5次
- **熔断行为**：状态切换为 error，停止所有线程，清空队列
- **自动恢复**：熔断5分钟后自动重置计数，尝试恢复运行
- **成功重置**：任意一次成功执行均重置失败计数为0
- **事件通知**：熔断触发时发布事件，UI 可展示告警

### 3.9 每日运行上限控制

管理每日运行时长和操作次数的上限，到上限后自动停止：

- **每日时长上限**：默认8小时，累计运行时长达到后停止调度
- **每日操作上限**：默认2000次操作，累计操作次数达到后停止调度
- **触发行为**：任意上限达到时发布 `run_limit_reached` 事件，执行收尾流程
- **计数方式**：每次任务执行时累加操作次数，运行时持续累加时长
- **每日重置**：凌晨00:00自动重置今日计数（与游戏重置时间同步）
- **配置可调**：上限值通过配置模块读取，支持用户自定义

### 3.10 任务依赖感知

填充线程在入队前感知任务间的依赖关系：

- 任务定义中声明 `depends_on` 依赖列表
- `get_due_tasks()` 返回结果中自动过滤掉依赖未完成的任务
- 依赖未完成的任务不入队，等待下一轮填充时重新检查
- 避免因依赖缺失导致任务执行失败

### 3.11 收尾流程

运行结束时统一执行收尾：

1. **清空 FIFO 队列**：丢弃所有未执行的任务
2. **停止两个线程**：终止填充线程和执行线程
3. **生成运行摘要**：运行起止时间、总运行时长、各任务执行统计
4. **保存调度状态**：将 task_state 原子写盘
5. **更新运行状态**：将 run_status 更新为 stopped
6. **断开连接**：断开模拟器连接
7. **通知 UI**：通过事件总线发布运行摘要

## 四、重点功能

### 4.1 双线程队列架构

填充线程和执行线程通过 FIFO 队列解耦，互不阻塞。填充线程只管"找任务入队"，执行线程只管"取任务执行"，两者可各自独立运作。

### 4.2 FIFO 队列 + 优先级入队

队列采用先进先出模式，先到期的任务先执行。入队时按优先级排序，优先级相同则按计算机查到的先后顺序入队。逻辑清晰，无调度歧义。

### 4.3 持续填充机制

填充线程不受队列状态影响，每轮都完整检查所有到期任务，确保新到期的任务不会因为"错过检查窗口"而延迟执行。

### 4.4 强制停止机制

用户点击停止按钮后，立即中断填充线程和执行线程，清空队列，不等当前步骤完成。停止后自动执行收尾流程，保证状态不丢失。

### 4.5 熔断保护

连续失败自动熔断，避免死循环浪费操作次数。熔断后自动计时恢复，成功执行自动重置计数。

### 4.6 异常分级恢复

按异常类型分级处理：可重试的自动重试，可恢复的尝试恢复，致命的立即停止。每种异常都有明确的恢复路径和终止条件。

## 五、实现思路

### 5.1 模块结构

```
core/
├── run_controller.py     ← 运行控制主入口：状态管理 + 双线程调度 + 收尾
├── run_state.py          ← 运行状态枚举定义
└── task_queue.py         ← FIFO 任务队列（线程安全，支持并发读写）
```

### 5.2 核心方法定义

从程序实现角度，`RunController` 类包含以下方法：

**生命周期控制方法（公开，供外部调用）**：

| 方法签名 | 可见性 | 所属类 | 作用 |
|---------|--------|--------|------|
| `start() -> bool` | 🔓 公开 | `RunController` | 允许性检查 → 初始化连接 → 加载状态 → 置 running → 启动双线程 |
| `stop() -> None` | 🔓 公开 | `RunController` | 设置 _stop_event → 中断双线程 → 清空队列 → 执行收尾 → 置 stopped |
| `pause() -> None` | 🔓 公开 | `RunController` | 设置 _pause_event → 等待当前任务完成 → 线程休眠 |
| `resume() -> None` | 🔓 公开 | `RunController` | 清除 _pause_event → 唤醒双线程 → 继续运行 |

**事件订阅（内部注册，通过事件总线触发）**：

| 方法签名 | 可见性 | 所属类 | 作用 |
|---------|--------|--------|------|
| `_on_start_requested() -> None` | 🔒 私有 | `RunController` | 收到 `start_requested` 事件，调用 `start()` |
| `_on_stop_requested() -> None` | 🔒 私有 | `RunController` | 收到 `stop_requested` 事件，调用 `stop()`（强制） |
| `_on_pause_requested() -> None` | 🔒 私有 | `RunController` | 收到 `pause_requested` 事件，调用 `pause()` |
| `_on_resume_requested() -> None` | 🔒 私有 | `RunController` | 收到 `resume_requested` 事件，调用 `resume()` |
| `_on_limit_reached() -> None` | 🔒 私有 | `RunController` | 收到 `run_limit_reached` 事件，调用 `stop()`（优雅） |

**线程主循环（私有，在独立线程中运行）**：

| 方法签名 | 可见性 | 所属类 | 作用 |
|---------|--------|--------|------|
| `_filler_loop() -> None` | 🔒 私有 | `RunController` | 填充线程主循环：检查 → get_due_tasks → 排序 → 入队 → 发布事件 → 休眠 |
| `_executor_loop() -> None` | 🔒 私有 | `RunController` | 执行线程主循环：出队 → 构造 context → 创建子线程 → 执行 → mark_done → 记录指标 |
| `_execute_single_task(name) -> TaskResult` | 🔒 私有 | `RunController` | 构造 TaskContext → `task.execute(context)` → 返回结果 |

**辅助方法（私有）**：

| 方法签名 | 可见性 | 所属类 | 作用 |
|---------|--------|--------|------|
| `_check_run_allowed() -> bool` | 🔒 私有 | `RunController` | 允许性检查：上限 + 连接 + 配置 |
| `_check_circuit_breaker() -> bool` | 🔒 私有 | `RunController` | 熔断检查：是否触发熔断 |
| `_handle_task_result(name, result) -> None` | 🔒 私有 | `RunController` | 处理 TaskResult：四种状态分派 |
| `_cleanup() -> None` | 🔒 私有 | `RunController` | 收尾：生成摘要 → 保存状态 → 断连 |
| `_update_queue_state() -> None` | 🔒 私有 | `RunController` | 同步队列状态到 `_state_manager` |
| `_reset_daily_counters() -> None` | 🔒 私有 | `RunController` | 每日00:00重置今日计数 |

### 5.3 核心流程

**启动链路**：
```
接收 start_requested 事件
  → _on_start_requested()
  → start()
  → 允许性检查（防封号上限 + 连接状态）
  → 初始化连接
  → 加载调度状态
  → 初始化空 FIFO 队列
  → 状态置为 running
  → 启动填充线程 _filler_loop()
  → 启动执行线程 _executor_loop()
```

**运行态（双线程协作）**：
```
填充线程 _filler_loop()：检查 → get_due_tasks() → 排序 → 加锁 → 入队 → 解锁 → 发布事件 → 休眠
执行线程 _executor_loop()：加锁 → 出队 → 解锁 → execute_single_task() → mark_done → 记录指标
```

**停止链路（强制）**：
```
接收 stop_requested 事件
  → _on_stop_requested()
  → stop()
  → 设置 _stop_event
  → 中断填充线程和执行线程
  → 强制终止当前任务子线程
  → 清空 FIFO 队列
  → _cleanup（摘要 → 保存状态 → 更新状态 → 断开连接）
  → 状态置为 stopped
```

### 5.4 关键设计

- **双线程解耦**：填充线程和执行线程通过 FIFO 队列通信，各自独立运行互不阻塞
- **线程安全队列**：队列操作加锁，支持填充线程和执行线程并发读写
- **事件驱动**：启停信号通过事件总线传递，发布者和订阅者完全解耦
- **状态集中管理**：运行状态通过状态管理模块统一维护
