# 08-事件通信总线（Event Communication Bus）

> **类型**：支撑服务层  ｜  **对应说明书**：（新概念）  ｜  **说明**：解耦新增，模块间通信枢纽

---

## 一、目的与作用

**一句话定位**：模块间通信枢纽。采用发布-订阅模式，模块间不直接持有对方引用，通过事件总线间接通信，实现真正的解耦。

**为什么需要这个模块**：

没有事件总线时，模块间是网状直接调用（如 UI → RunController → Scheduler → Task → Connection），增删模块需修改所有相关代码。

有了事件总线后，发布者不关心谁订阅，订阅者不关心谁发布。增删模块只需增删订阅，不改现有代码。

```
用户点"停止" → UI 发布 "stop_requested"
  → RunController 订阅后执行停止逻辑
  → Scheduler 订阅后暂停调度
  → Task 订阅后中止当前步骤
  → Connection 订阅后断开连接
```

**核心职责**：
1. **事件发布**：发布事件，不关心谁在处理
2. **事件订阅**：订阅事件，支持按条件过滤
3. **线程安全**：跨线程发布/订阅（UI线程与工作线程通信）
4. **事件历史**：可选记录事件历史，便于调试

**设计原则**：
- **发布者不阻塞**：publish 立即返回，handler 异步执行
- **松耦合**：发布者和订阅者互不感知
- **事件命名规范**：过去式命名（如 task_done 而非 do_task）

| `_queue` | `Queue` | 异步事件队列（`queue.Queue` 线程安全），工作线程消费 |
| `_lock` | `Lock` | 保护 `_subscribers` 的线程安全。`subscribe()` / `unsubscribe()` 需获取 |
| `_stop_event` | `Event` | 停止信号。`stop()` 设置此事件，`_dispatch_thread` 检测到后退出循环 |

| `_history` | `deque[Event] \| None` | 可选的事件历史记录环形缓冲。`deque(maxlen=2000)`，通过构造函数参数 `enable_history=True` 启用 |
| `_last_event_cache` | `dict[str, float]` | 去重缓存：去重键 = `f"{name}:{dedup_key}"`。`publish()` 时检查，若 200ms 内相同去重键的事件则跳过不入队。`dedup_key` 默认取 `str(data)` 的前 64 字符，`state_changed` 等事件的发布者可传入更精确的 `dedup_key`（如对应状态键名），避免不同数据内容的同名事件被误去重。内部每 100 次 publish 清理超过 2s 的旧条目 |
| `_dedup_lock` | `Lock` | 保护 `_last_event_cache` 的线程安全 |
| `_publish_counter` | `int` | 自增计数器，每 100 次触发一次去重缓存过期清理 |

## 三、运行逻辑

### 3.1 发布-订阅流程

**订阅**：`subscribe(event_name, handler, filter?)` → 将 handler 注册到 event_name 的订阅者列表 → 返回订阅 ID（用于取消订阅）。

**发布**：`publish(event_name, source, dedup_key=None, **data)` → 去重检查（`_dedup_lock` 保护，`_last_event_cache` 中 200ms 内相同去重键跳过）。去重键 = `f"{name}:{dedup_key or str(data)[:64]}"`。`state_changed` 等事件的发布者可传入更精确的 `dedup_key`（如 `event.data["key"]`），避免不同数据内容的同名事件被误去重。→ 封装 Event 对象（name、data、timestamp、source）→ 放入异步队列 → 立即返回。

**分发**：工作线程循环检测 `_stop_event`，从队列取出事件（timeout=1s）→ 浅拷贝订阅者列表 → **串行遍历** handler（同一事件的多个订阅者在此单线程中按注册顺序依次执行，无并发）。filter 返回 False 跳过 → 执行 handler 记录耗时 → 超过 5s 记录软超时警告 → 异常捕获不中断循环 → 启用历史则追加到 `_history`。

> **Handler 串行执行的影响**：由于订阅者在同一线程中串行执行，前一个 handler 的耗时将延迟后续所有 handler。**耗时操作或 I/O 密集型任务（如写日志、网络请求）应在 handler 内部自行开线程处理**，避免阻塞分发线程和后续订阅者。

### 3.2 线程安全

- **`_lock`**（`threading.Lock`）：保护 `_subscribers` 注册表的并发访问。`subscribe()` / `unsubscribe()` 必须获取锁。分发时浅拷贝订阅者列表（副本不持锁），避免遍历时被修改导致 `RuntimeError`
- **`_dedup_lock`**（`threading.Lock`）：保护 `_last_event_cache` 去重缓存的并发访问。`publish()` 的检查-更新操作为原子序列
- **`_queue`**（`queue.Queue`）：跨线程通信核心，发布者线程入队不阻塞，工作线程出队消费。可配置 `maxsize=1000` 提供背压保护
- **`_stop_event`**（`threading.Event`）：跨线程停止信号，`stop()` 设置事件，工作线程轮询检测后退出循环

### 3.3 性能保障

| 优化点 | 策略 | 说明 |
|-------|------|------|
| **异步分发** | publish 入队即返回 | 发布者线程不等待 handler 执行完成 |
| **handler 软超时** | 单个 handler 执行超过 5 秒记录警告日志，但**不中断 handler 执行** | 防止慢 handler 阻塞后续事件的排查（Python 无法安全终止正在执行的函数，故采用软超时） |
| **异常隔离** | 单个 handler 异常不影响其他 | 不中断分发循环 |
| **去重合并** | `publish()` 在 `_dedup_lock` 保护下检查 `_last_event_cache[dedup_key]`，去重键 = `f"{name}:{dedup_key or str(data)[:64]}"`，200ms 内相同去重键的重复事件跳过不入队 | 防止事件风暴（如连续 `schedule_updated`），队列不会被次要事件淹没。去重键包含数据摘要，不同数据内容的同名事件（如 `state_changed` 的不同 key）不会被误去重 |
| **去重缓存清理** | 每 100 次 `publish()` 执行一次过期条目清理（超过 2s 的旧条目移除），而非每次遍历 | 30+ 条目的遍历耗时在微秒级，计数器优化仅作为预防性设计，不影响功能 |
| **队列背压** | `Queue(maxsize=1000)`，`put(block=True)`：队列满时阻塞发布者直到有空位 | 事件不丢失优先于发布者不阻塞——控制类事件（如 `stop_requested`）绝不能丢。如果后续发现性能瓶颈，可改为 `put(timeout=0.5)` + 超时后根据事件类型决定丢弃或重试 |

### 3.4 事件命名规范

事件名采用过去式，统一格式如 `stop_requested`、`run_started`、`task_done`、`connection_lost`。通过 Events 常量类统一管理，避免字符串拼写错误。

## 四、重点功能

### 4.1 完全解耦

模块间通过事件通信，不持有对方引用。发布者不知道谁在处理事件，订阅者不知道谁发布了事件。新增功能只需新增订阅，无需修改现有代码。

### 4.2 条件过滤

订阅时传入 filter 函数，只有满足条件的事件才触发 handler。避免订阅者收到无关事件后自行判断。

### 4.3 事件历史

可开启事件历史记录（构造函数参数 `enable_history=True`），使用 `deque(maxlen=2000)` 记录所有发布的事件（含时间戳和数据），便于调试时追溯"发生了什么"。历史记录有上限，不会无限增长。

## 五、实现思路

### 5.1 模块结构

```
core/
├── event_bus.py          ← EventBus 事件总线主入口（异步队列 + 去重 + 软超时 + 历史）
└── events.py             ← Events 事件名常量定义（集中管理全部 ~27 个事件名）
```

### 5.2 核心数据结构和类型签名

**Event（事件对象）**：
```
@dataclass
class Event:
    name: str              # 事件名，如 "task_done"
    data: dict             # 事件数据，发布者传入的 **data
    timestamp: float       # 事件发布时间戳（time.time()）
    source: str            # 发布者模块名（可选，由发布者传入或自动记录）
```

**Handler 签名**：`handler(event: Event) -> None`
- 订阅者提供的回调函数，接收一个 `Event` 对象
- 返回值忽略。异常不会传播到分发循环（异常隔离）
- **同步执行**：handler 在工作线程中同步执行，应当尽快返回。如需耗时操作应自行开线程

**Subscriber（订阅者注册条目）**：
```
@dataclass
class Subscriber:
    id: str                # 唯一订阅 ID（UUID4 字符串）
    handler: callable      # handler(event: Event) -> None
    filter: callable | None # filter(event: Event) -> bool，返回 False 跳过
```

**Filter 签名**：`filter(event: Event) -> bool`
- 订阅时传入的可选过滤函数
- 返回 True 执行 handler，返回 False 跳过
- 不传 filter 时默认处理所有事件

**Subscription ID**：`subscribe()` 返回 UUID4 十六进制字符串（如 `"a1b2c3d4e5f6"`），通过 `uuid.uuid4().hex` 生成。订阅者需保存此 ID 用于 `unsubscribe()`。

### 5.3 核心方法定义

**EventBus（事件总线）**：

| 方法签名 | 可见性 | 所属类 | 作用 |
|---------|--------|--------|------|
| `publish(name, source, dedup_key=None, **data) -> None` | 🔓 公开 | `EventBus` | 发布事件。`name` 事件名，`source` 发布者模块名，`dedup_key` 可选去重键（默认取 `str(data)[:64]`）。去重检查（200ms 内相同去重键跳过）→ 封装 Event(name, data, timestamp, source) → 入队 → 立即返回 |
| `subscribe(name, handler, filter) -> str` | 🔓 公开 | `EventBus` | 订阅事件。生成 UUID4 订阅 ID → 加锁注册 → 返回 ID |
| `unsubscribe(sub_id) -> None` | 🔓 公开 | `EventBus` | 按订阅 ID 取消订阅。加锁遍历 `_subscribers` 移除匹配条目 |
| `stop() -> None` | 🔓 公开 | `EventBus` | 停止事件总线。设置 `_stop_event` → 等待 `_dispatch_thread` join(timeout=3) → **清空队列（丢弃队列中所有未处理事件）**。关闭时由 16-应用启动引导 调用。**注意**：stop() 不处理队列中剩余事件，调用方应在 stop() 前确保所有业务模块已停止产生新事件
| `clear() -> None` | 🔓 公开 | `EventBus` | 清空所有订阅 + 清空队列 + 清空历史 + 重置 `_last_event_cache`（测试/重置用，不停止线程）。**与 `stop()` 的区别**：`clear()` 保留线程，可用于模块间重置；`stop()` 销毁分发线程，用于程序关闭 |

### 5.4 核心流程

**事件发布与分发流程**（含去重 + 软超时 + 停止信号）：
```
任意模块.publish("schedule_updated", "05-时间调度模块", queue=[...])
  → 计算去重键: dedup_key = f"{name}:{dedup_key or str(data)[:64]}"
     （如 state_changed 的发布者可传入 dedup_key=event.data["key"]）
  → 获取 _dedup_lock
  → 检查 _last_event_cache 中 dedup_key 的上次发布时间
  ├── 存在且时间差 < 200ms？→ 释放 _dedup_lock，跳过
  └── 否则 → 更新 _last_event_cache[dedup_key] = now
         → _publish_counter += 1
         → if _publish_counter % 100 == 0:  # 每 100 次清理一次过期条目
              → 遍历 _last_event_cache，移除 timestamp < now - 2s 的条目
         → 释放 _dedup_lock
         → 封装 Event(name, data, timestamp, source)
         → _queue.put(event, block=True)（队列满时阻塞，不丢事件）
  → 返回

_dispatch_thread 工作线程主循环：
  while not _stop_event.is_set():
    → 从 _queue 取出 Event（timeout=1.0，超时后重新检查 stop_event）
    → event 为 None（超时）→ 回到循环开头
    → 查找 _subscribers[event.name]（浅拷贝列表，避免遍历时被 unsubscribe 修改）
    → 遍历 subscriber 列表：
        ├── filter 存在且返回 False？→ 跳过
        ├── 记录 start_time = time.time()
        ├── 调用 subscriber.handler(event)
        ├── 执行完毕 → 记录耗时
        ├── 耗时 > 5s？→ 记录 "handler 执行超时: {name} {耗时}s" 警告（不中断 handler）
        └── 异常？→ 捕获异常 → 记录 "handler 异常: {name} {error}" → 继续下一个
    → _history 启用？→ _history.append(event)
```

**订阅注册流程**（线程安全）：
```
任意模块.subscribe("state_changed", handler, filter=None)
  → 生成 UUID4 订阅 ID: sub_id = uuid.uuid4().hex
  → 获取 _lock
  → 创建 Subscriber(id=sub_id, handler=handler, filter=filter)
  → 追加到 _subscribers.setdefault("state_changed", [])
  → 释放 _lock
  → 返回 sub_id
```

**停止流程**（丢弃队列中剩余事件，不等待处理）：
```
stop()
  → 设置 _stop_event（通知工作线程退出循环）
  → 等待 _dispatch_thread join(timeout=3)
  ├── 正常退出 → 记录 "事件总线已停止" INFO
  └── 超时 → 记录 "事件总线分发线程未在 3s 内退出" WARNING
       （线程是 daemon=True，进程退出时自动终止）
  → 清空 _queue（丢弃所有未处理事件）
  → 调用方（16-应用启动引导）应在 stop() 前确保各模块已停止发布新事件
```

### 5.5 关键设计

- **异步队列**：publish 入队立即返回，工作线程异步分发，不阻塞发布者
- **异常隔离**：单个 handler 异常不影响其他订阅者
- **线程安全**：Lock 保护订阅者列表，Queue 实现跨线程通信（UI 线程 ↔ 工作线程）
- **条件过滤**：subscribe 支持 filter 参数，订阅者可只处理关心的事件
- **去重合并**：`dict[str, float]` 按去重键 `f"{name}:{data_signature}"` 追踪最后发布时间，`_dedup_lock` 保护线程安全。200ms 内相同去重键的事件跳过不入队。去重键包含数据摘要，不同数据内容的同名事件不会误去重。超过 2s 的旧条目自动清理
- **无优先级队列**：所有事件共用同一 FIFO 队列，无优先级区分。控制类事件（如 `coordinate_action`、`stop_requested`）与高频事件（如 `log_record`）同等排队。若队列积压，控制事件的延迟会增大。这是一个**已知限制**，未来可按需引入高优先级通道
- **handler 软超时**：handler 执行超过 5s 记录警告但不中断（Python 无法安全终止正在执行的函数）
- **停止信号**：`_stop_event` 控制分发线程退出，`stop()` 提供优雅关闭。**`stop()` 丢弃队列中所有未处理事件**，调用方应确保 `stop()` 前各模块已停止发布
- **Handler 串行执行**：同一事件的订阅者在分发线程中按注册顺序串行执行。耗时操作应在 handler 内部自行开线程，避免阻塞后续订阅者
- **Event 统一结构**：`name`/`data`/`timestamp`/`source` 四字段，Handler 签名 `handler(event: Event)`
- **Subscriber 注册**：UUID4 订阅 ID + handler + filter 三元组，加锁注册
- **事件名常量**：`Events` 类统一管理 27 个事件名，避免拼写错误
- **全局单例**：整个程序共享一个 EventBus 实例。由 **16-应用启动引导** 在 `start()` 中创建，通过构造函数注入给各模块（与依赖注入保持一致）。不采用模块级全局变量，便于测试时替换为 mock 实例
- **与 StateManager 的职责分工**：`StateManager` 内部的 `subscribe()` 仅用于其自身向 EventBus 订阅 `state_changed` 事件后的内部分发（按 key 路由给本地 `_subscribers`）。**所有外部模块对状态变更的订阅，一律通过 `EventBus.subscribe("state_changed", handler)` 进行**，不通过 `StateManager.subscribe()`。EventBus 是唯一的模块间通信入口，`StateManager.subscribe()` 是对内的分发辅助，不对外。

## 六、使用方法（模块间交互）

### 6.1 外部提供的调用接口

| 调用接口 | 调用方 | 说明 |
|---------|--------|------|
| `publish(event_name, source, **data)` | 所有模块 | 发布事件，异步分发。`source` 为发布者模块名 |

| `clear()` | 测试/重置 | 清空所有订阅 + 队列 + 历史 + 去重缓存 |

### 6.3 使用方式

各模块在初始化时通过 `event_bus.subscribe()` 订阅关心的事件，在适当的时候通过 `event_bus.publish()` 发布事件。全局单例 `event_bus` 由 **16-应用启动引导** 在 `start()` 中创建，通过构造函数注入给各模块。

### 6.4 对外部模块的调用

| 被调用方 | 调用方式 | 说明 |
|---------|---------|------|
| **12-日志监控中心** | 写入 | 记录事件处理异常日志（可选） |
| **16-应用启动引导** | 调用 `stop()` | 程序关闭时停止事件总线，清理分发线程 |
| **测试/重置** | 调用 `clear()` | 清空所有订阅和队列，用于模块级测试 |
