## 一、目的与作用

**一句话定位**：时间调度引擎。根据每个任务的执行规则和 next_run_time，提供批量到期查询和调度推进能力，供运行控制中心驱动任务执行。

**与运行控制中心的职责拆分**：
- **运行控制中心**（09）：生命周期管理——ScriptWorker 线程驱动调度循环、执行任务、响应停止
- **时间调度模块**（05）：纯调度——只回答"哪些任务已到期"并推进 next_run_time

**核心职责**：
1. **时间规则管理**：解析每个任务的 10 种重复规则类型（含 `on_enter` 启动执行、`trigger` 特殊条件触发）
2. **next_run_time 机制**：到期判据（当前时间 ≥ next_run_time + 三重过滤）
3. **批量到期查询**：`build_schedule()` 返回当前所有到期任务列表，按优先级排序
4. **执行推进**：`mark_done()` 成功后按执行模式/规则推进 next_run_time，失败添加递增冷却
5. **状态持久化**：`TaskStateStore` 原子写盘 `task_state.json`，重启恢复
6. **次数控制**：`max_daily` / `today_count` / `fail_streak` 冷却 + `total_count` 活动累计上限
7. **活动有效期**：支持 `active_range` 日期范围 + 每日时间窗口（单时段 `time_start/time_end` 或多时段 `time_slots`）
8. **执行模式**：`execution_mode` 决定推进节奏——`daily`（按天执行一次）/ `per_slot`（每时间段各执行一次），配合 `max_daily` 限制每日执行次数
9. **活动日历导入**：`import_calendar(events)` 批量导入限时活动，自动更新任务配置
10. **配合定时启停**：为 09-运行控制中心 的全局运行时段（`global.schedule`）提供调度状态查询

**设计原则**：
- **纯调度职责**：只回答"哪些任务已到期"，不关心队列和执行状态
- **失败不推进**：临时失败不推进 next_run_time，保持到期可重试
- **持久化优先**：每次状态变更立即原子写盘，重启不丢失
- **调度解耦**：09 通过 `get_next_task()` 主动拉取，不依赖事件推送

## 三、运行逻辑

### 3.1 到期判据（三重条件）

任务可执行需同时满足以下三项：

1. **时间已到**：当前时间 ≥ `next_run_time`
2. **在每日时间窗口内**：单时段 `time_start ~ time_end` 或多时段 `time_slots`（落在任一时段内即可）。均未设置则全天可执行
3. **在活动有效期内**：当前日期在 `active_range` 范围内。未设置则永久有效

三项全部满足才算到期，缺一不可。

> **触发式任务（`repeat.type=trigger`）例外**：不走时间判据。任务不设置
> 初始 `next_run_time`，也不由时间推进——到期完全由外部触发驱动：
> - **手动触发**：UI"手动触发"按钮 / 外部调用 `update_next_run(name, now)`
> - **识图触发**：02-图像识别模块 的 TriggerWatcher 识别到触发模板 → 发布
>   `trigger_detected` 事件 → 本模块订阅后内部调 `update_next_run(name, now)`
> 一旦 `next_run_time` 被置为当前时刻，该任务立即满足"时间已到"，且触发式任务
> 不配时间窗口/活动有效期（其余判据恒通过）→ 自动入队执行。

### 3.2 日程表生成（build_schedule）

由 ScriptWorker（09-运行控制）调度循环调用：

```
① [获取 _lock]
②   检查跨日 → 如需重置则 reset_daily_counters()（持锁重置，确保 DAILY_RESET 事件不会与 mark_done 交错）
③   遍历所有启用任务
④   对每个任务:
        状态过滤：task_status = completed / skipped → 直接跳过（不进入日程）
                  ★ 关键拦截：on_enter / trigger 执行后 next_run 不推进（时间一直"到"），
                    靠 completed 状态拦截防止反复入队；max_daily 满、total_count 满、
                    熔断同样靠此过滤
        is_due(task_name) → 三重判据（窗口判断支持单时段/多时段）
        check_times_limit(task_name) → today_count < max_daily?
        execution_mode 判定 → daily 已执行过则跳过；per_slot 今日已满 max_daily 则跳过
⑤   过滤掉未到期/达上限的任务
⑥   按 priority 升序 → 同优先级按 category 顺序排序
⑦ [释放 _lock]
⑧ 发布 SCHEDULE_UPDATED 事件到 UI（此时已无锁，订阅者可安全调用其他调度方法）
⑨ 返回排序后的日程列表
```

### 3.3 执行推进（mark_done）

```
mark_done(name, success=True):
  ① 成功后 fail_streak 归零；today_count += 1；total_count += 1
  ② 按执行模式推进 next_run_time（本质：计算下一次执行时间）：
      · 多时段 time_slots 存在时，按 execution_mode 推进：
          execution_mode = daily    → 推进到次日首个时段起点（一天只执行一次）
          execution_mode = per_slot → 推进到下一个时段起点（每时段各执行一次；
                                      今日已达 max_daily → 标记今日 completed）
      · 无多时段时按 RepeatRule.type 推进:
          once         → 标记完成，不再调度
          daily        → 推进到次日 time_start
          weekly       → 推进到下周匹配 weekday
          monthly_start→ 推进到下月 1 号
          interval_days→ 推进 N 天后
          interval_hours→推进 N 小时后
          expire_at    → 不自动推进，等待 report_expire()
          special      → 同 daily，受 window.date 限制
          on_enter     → 标记完成（本轮运行不再执行；下次启动 load_state() 重置 next_run 重新激活）
          trigger      → 标记完成 + 清空 next_run（不再自推进，等待外部再次触发；
                         重启 load_state() 不自动激活——区别于 on_enter）
  ③ 累计次数达 total_count 上限 → 标记永久完成（不再调度）
  ④ save_state() 原子写盘

mark_done(name, success=False):
  ① fail_streak += 1
  ② 检查 fail_streak ≥ max_fail_streak（默认 10，可在 TaskConfig 覆盖）？
     ├── 是 → 熔断：标记任务为 skipped，不再调度此任务
     │        发布 TASK_SKIPPED 事件（reason="连续失败熔断"）
     │        不推进 next_run_time，不保存冷却
     └── 否 → 继续冷却
        ③ 添加递增冷却: next_run = now + min(fail_streak × 5min, 60min)
        ④ 不推进原 next_run_time
  ⑤ save_state() 原子写盘
```

### 3.4 每日重置

```
check_daily_reset():
  ① 检查当前日期 > _last_daily_reset
  ② 是 → 所有任务 today_count = 0
  ③ 更新 _last_daily_reset = 今天
  ④ 发布 DAILY_RESET 事件
```

### 3.5 活动日历导入（import_calendar）

```
import_calendar(events: list[CalendarEvent]):
  ① 接收活动事件列表（见 5.2 CalendarEvent 定义）
  ② 遍历事件:
      若有同名任务 → 更新其 active_range / window
      若无同名任务 → 新建 special 类型任务
  ③ save_state() 原子写盘
  ④ 返回 (更新数, 新建数)
```

### 3.6 异常恢复流程

| 异常场景 | 恢复步骤 |
|---------|---------|
| ① task_state.json 损坏 | `load_state()` 捕获 `JSONDecodeError` → 初始化空状态 → 重新从 `tasks.yaml` 计算所有 `next_run_time` → `save_state()` |
| ② task_state.json 不存在（首次运行） | `load_state()` 捕获 `FileNotFoundError` → 初始化空状态 → 第一天运行，无历史记录 |
| ③ tasks.yaml 中任务被删除 | `load_tasks_from_config()` 自动跳过 `_store` 中不存在于新配置的任务记录 |
| ④ next_run_time 丢失 | `register_task()` 时若 `_store.get(name)` 为 None → 调用 `RepeatRule.get_initial_next_run()` 计算初始值 |
| ⑤ 磁盘写失败 | `save_state()` 中 `shutil.move()` 异常 → 保留临时文件 → 下次 `load_state()` 时自动清理 `.tmp` 文件 |

## 四、重点功能

### 4.1 纯调度解耦

只回答"哪些任务已到期"，不涉及运行生命周期。09-运行控制中心 通过 `get_next_task()` 主动拉取，保持调度与执行的职责边界清晰。

### 4.2 失败不推进 + 递增冷却 + 熔断

任务执行失败不推进 `next_run_time`，保持到期可重试。同时添加递增冷却（5→10→15→...→60 分钟），防止死循环反复重试失败任务。成功后 `fail_streak` 自动归零。

当 `fail_streak` 达到 `max_fail_streak`（默认 10，可在任务配置中覆盖）时触发**熔断**：标记任务为 `skipped`，`skip_reason="fail_streak"`，不再调度此任务，发布 `TASK_SKIPPED` 事件。

**不可恢复错误熔断**：当 04-任务执行引擎 报告 `UnrecoverableError`（如配置错误、素材缺失导致无法执行）时，标记任务为 `skipped`，`skip_reason="unrecoverable"`。此类熔断**不在重启时自动恢复**，必须由用户在 UI 面板手动重置。

**熔断恢复方式**（两种）：
- **自动恢复**（仅 `skip_reason="fail_streak"`）：脚本重启时 `load_state()` 自动对所有 `skip_reason="fail_streak"` 的任务调用 `reset_fail_streak()`，清除 `skipped` 状态，任务恢复正常调度
- **手动恢复**：用户通过 UI 面板的"重置失败计数"按钮调用 `reset_fail_streak(task_name)`，清除任意类型的 `skipped` 状态

此机制与 04-任务执行引擎 的熔断形成双重保护——04 防止单次执行死循环，05 防止跨会话持续失败。

### 4.3 原子持久化

`TaskStateStore.save()` 使用 `tempfile.mkstemp() + shutil.move()` 实现原子写盘。崩溃不损坏已有数据，重启后从 `config/runtime/task_state.json` 恢复所有任务的 `next_run_time` 和 `today_count`。

### 4.4 三重时间过滤

`is_due()` 同时检查 `next_run_time`、每日时间窗口（单时段 `time_start~time_end` 或多时段 `time_slots`）、活动 `active_range` 日期范围。三项全部满足才算到期，支持灵活的时间策略组合。多时段下每个时段起点作为 `next_run_time` 触发点；`execution_mode=daily` 每天只执行一次（执行后推到次日），`execution_mode=per_slot` 每个时段各执行一次（配合 `max_daily` 可限制每日执行次数，如 5 个时段只执行前 2 个）。

### 4.5 活动日历导入

`import_calendar(events)` 批量导入限时活动数据，自动为活动期间的任务设置 `active_range` 和 `window`。活动结束后自动禁用对应任务，无需手动维护。

### 4.6 每日重置

每日 00:00 自动重置所有任务的 `today_count`，与阴阳师游戏重置时间保持一致。`check_daily_reset()` 在每次 `build_schedule()` 调用时惰性检查。

## 五、实现思路

### 5.1 模块结构

```
core/
├── scheduler.py          ← 调度引擎主入口 Scheduler
├── repeat_rule.py        ← RepeatRule 执行规则定义与推进逻辑
└── task_state.py         ← TaskState 执行记录持久化 + TaskStateStore
```

### 5.2 核心数据结构

**TaskConfig（任务配置）**—— 从 `tasks.yaml` 加载的单个任务完整配置：
| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | `str` | 任务唯一标识，如 "yuhun" |
| `display_name` | `str` | 显示名，如 "御魂副本" |
| `enabled` | `bool` | 是否启用（默认 true） |
| `category` | `str` | 分类：`daily`/`permanent`/`event`/`special` |
| `priority` | `int` | 优先级（1~99，越小越优先，默认 10） |
| `repeat` | `RepeatConfig` | 重复规则配置（见下） |
| `max_daily` | `int \| None` | 每日最大执行次数，None 表示不限制 |
| `max_fail_streak` | `int` | 熔断阈值（默认 10），连续失败达此值后跳过任务 |
| `active_range` | `list[str] \| None` | 活动有效期，`["2026-07-20", "2026-08-20"]`，None 表示永久有效 |
| `time_start` | `str \| None` | 每日开始时间 `"08:00"`，None 表示不限制（单时段，与 `time_slots` 互斥） |
| `time_end` | `str \| None` | 每日结束时间 `"23:00"`，None 表示不限制（单时段，与 `time_slots` 互斥） |
| `time_slots` | `list[list[str]] \| None` | 多时段，如 `[["10:00","12:00"],["12:00","14:00"],["14:00","16:00"]]`。存在 2+ 时段时优先于 `time_start/time_end` |
| `execution_mode` | `str` | 执行模式：`daily`（按天执行一次，默认）/ `per_slot`（每时间段各执行一次）。替代原 `execution_rule` 的"每日轮次"语义 |
| `total_count` | `int \| None` | 累计执行次数上限（活动期累计），None 表示不限制 |
| `team_id` | `str \| None` | 阵容预设 ID（战斗任务） |
| `floor` | `int \| None` | 副本层数 |

> **触发式任务（`repeat.type=trigger`）**：不需要 `time_start`/`time_end`/`time_slots`/
> `execution_mode`/`active_range` 等时间字段（配置了也不生效）。任务无初始
> `next_run_time`，仅在外部触发（手动 `update_next_run` / TriggerWatcher 识图命中
> 发布 `trigger_detected`）时才被置为到期入队；执行完成后进入已失效
> （标注"等待下次触发"）。

**RepeatConfig（重复规则配置）**：
| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | `str` | 规则类型：`once`/`daily`/`weekly`/`monthly_start`/`interval_days`/`interval_hours`/`expire_at`/`special`/`on_enter`（每次运行启动后执行一次）/`trigger`（特殊条件触发） |
| `value` | `int \| None` | 间隔值（`interval_days=3` 表示每3天，`weekly` 的 weekday 数字） |
| `weekday` | `int \| None` | `weekly` 类型专属：0=周一~6=周日 |
| `window` | `dict \| None` | `special` 类型专属：`{date: "2026-07-22", start: "10:00", end: "12:00"}` |
| `expire_at` | `str \| None` | `expire_at` 类型专属：到期日期 `"2026-08-20"`，到期后不再调度 |
| `loop_count` | `int \| None` | 总循环次数（副本战斗次数），None 表示不限制 |
| `monthly_day` | `int` | `monthly_start` 类型专属：每月几号执行（默认 1，可设为 1~28） |
| `trigger_templates` | `list[str] \| None` | `trigger` 类型专属：触发模板识别列表，如 `["trigger/activity_enter"]`（对应 assets/ 素材）。02-TriggerWatcher 监控到任一模板命中 → 发布 `trigger_detected` 触发该任务 |

**TaskInfo（日程条目）** —— `build_schedule()` 和 `schedule_queue` 的条目：
| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | `str` | 任务名 |
| `priority` | `int` | 优先级 |
| `category` | `str` | 分类 |
| `next_run` | `datetime` | 下次执行时间 |
| `status` | `ScheduleStatus` | 当前调度状态 |

**ScheduleStatus（调度状态枚举）**：
| 枚举值 | 说明 |
|--------|------|
| `due` | 已到期，等待执行 |
| `waiting` | 未到期，等待时间到达 |
| `completed` | 今日已完成（已达 `max_daily` / `per_slot` 已执行满）或活动期累计达 `total_count` 上限 / `on_enter` 本轮已执行 / `trigger` 本轮已执行（等待下次触发） |
| `skipped` | 被跳过（熔断、依赖未满足等） |

**UI 队列归属**（11-用户界面模块 队列面板四区，§3.2）：
| 状态 | UI 归属 | 标注 |
|------|--------|------|
| `due` | ⏳ 待执行 | 任务名 + 下次执行时间 |
| `waiting` | 🕐 未开始 | 任务名 + 下次执行时间 |
| `completed`（max_daily / per_slot 满 / total_count 满） | ⚠ 已失效 | `[已过期] · 累计 x/y 次已完成` 等 |
| `completed`（on_enter 本轮已执行） | ⚠ 已失效 | **`[本轮已完成] · 下次启动执行`** |
| `completed`（trigger 本轮已执行） | ⚠ 已失效 | **`[等待下次触发] · 外部触发后重新激活`** |
| `skipped` | ⚠ 已失效 | `[已跳过]`（熔断） |

**TaskState（持久化状态）** —— `task_state.json` 中每个任务的存储结构：
| 字段 | 类型 | 说明 |
|------|------|------|
| `task_name` | `str` | 任务名 |
| `next_run_time` | `str` | ISO 格式的下次执行时间，如 `"2026-07-24T06:00:00+08:00"` |
| `today_count` | `int` | 今日已执行次数 |
| `fail_streak` | `int` | 当前连续失败次数 |
| `last_done` | `str \| None` | 上次执行完成时间（ISO 格式） |
| `last_status` | `str \| None` | 上次执行结果：`success`/`fail` |
| `skip_reason` | `str \| None` | 熔断原因。`"fail_streak"`（连续失败熔断，重启可自动恢复）/ `"unrecoverable"`（不可恢复错误，必须手动重置）。为 None 表示未被熔断。`load_state()` 只对 `skip_reason="fail_streak"` 的任务自动调用 `reset_fail_streak()`，`"unrecoverable"` 跳过自动恢复 |
| `updated` | `str` | 最后更新时间（ISO 格式） |

**CalendarEvent（活动日历事件）** —— `import_calendar()` 的参数条目：
| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | `str` | 活动名称，与任务名匹配（精确匹配，建议使用与 tasks.yaml 一致的 name） |
| `start` | `str` | 开始日期 `"2026-07-20"` |
| `end` | `str` | 结束日期 `"2026-08-20"` |
| `window` | `dict \| None` | 每日时间窗口 `{start: "10:00", end: "12:00"}` |
| `type` | `str \| None` | 规则类型，默认 `special` |

> **时区策略**：所有时间存储和比较统一使用 UTC+8（`datetime.timezone(datetime.timedelta(hours=8))`），与阴阳师服务器时间一致。配置中的 `time_start`/`time_end` 均为 UTC+8 的本地时间。`RepeatRule` 解析时自动附加时区信息。

### 5.3 核心方法定义

**Scheduler（调度引擎主入口）**：

| 方法签名 | 可见性 | 所属类 | 作用 |
|---------|--------|--------|------|
| `load_tasks_from_config() -> None` | 🔓 公开 | `Scheduler` | 从 `tasks.yaml` 加载所有任务并注册 |
| `load_state() -> None` | 🔓 公开 | `Scheduler` | 从 `config/runtime/task_state.json` 恢复执行记录。若文件不存在（首次运行）或 JSON 解析失败（损坏），初始化空状态后重新从 `tasks.yaml` 计算所有 `next_run_time`。原子写入损坏的 `.tmp` 文件在下次 `load_state()` 时自动清理。**启动恢复时，仅对 `skip_reason="fail_streak"` 的任务自动调用 `reset_fail_streak()`**，`"unrecoverable"` 的任务保持 `skipped` 状态（必须手动重置）。**`repeat.type=on_enter` 的任务启动恢复时重置为待执行**（next_run=启动时刻），确保每次运行都执行一次。**`repeat.type=trigger` 的任务启动恢复时不自动激活**（保持 completed/等待触发状态，直到外部再次触发）。**`_last_daily_reset` 初始化为 `date.today()`**——因 `today_count` 已从磁盘正确加载，当前日期就是今天，无需重复重置。此初始化防止重启后 `_last_daily_reset = None` 导致的错误跨日重置 |
| `save_state() -> None` | 🔓 公开 | `Scheduler` | 原子写盘保存状态 |
| `build_schedule() -> list[TaskInfo]` | 🔓 公开 | `Scheduler` | 生成完整日程表（排序+过滤），返回 TaskInfo 列表（含 name/priority/category/next_run/status）。**获取 `_lock` 读取数据构造列表后立即释放锁**，再发布 `SCHEDULE_UPDATED` 事件（避免持锁发布事件导致订阅者回调尝试获取 `_lock` 时死锁） |
| `get_next_task() -> str \| None` | 🔓 公开 | `Scheduler` | 获取下一个到期任务名（内部调用 `build_schedule()`）。**获取 `_lock` 后遍历 `_next_run`，避免与 `mark_done` 竞争** |
| `get_all_tasks() -> list[TaskConfig]` | 🔓 公开 | `Scheduler` | 获取所有已注册任务的 TaskConfig 列表（供 UI 展示） |
| `mark_done(task_name, success) -> None` | 🔓 公开 | `Scheduler` | 标记任务完成：成功按 `execution_mode` 推进 `next_run_time`（`daily`=次日首个时段 / `per_slot`=下一时段起点 / `on_enter`=本轮完成），失败添加递增冷却 |
| `is_due(task_name, now=None) -> bool` | 🔓 公开 | `Scheduler` | 判断任务是否到期（三重判据） |
| `check_times_limit(task_name) -> bool` | 🔓 公开 | `Scheduler` | 检查任务是否未达次数上限 |
| `update_next_run(task_name, next_run_time) -> None` | 🔓 公开 | `Scheduler` | 手动设置 `next_run_time`（UI / ParamBridge 调用）。**触发式任务触发入口**：置为当前时刻 → 立即到期入队 |
| `get_next_run_time(task_name) -> Optional[datetime]` | 🔓 公开 | `Scheduler` | 查询任务的 `next_run_time` |
| `reset_daily_counters() -> None` | 🔓 公开 | `Scheduler` | 每日 00:00 重置 `today_count` |
| `import_calendar(events: list[CalendarEvent]) -> tuple[int, int]` | 🔓 公开 | `Scheduler` | 导入游戏活动日历。events 参数结构见 5.2 CalendarEvent。返回 (更新数, 新建数) |
| `report_expire(task_name) -> None` | 🔓 公开 | `Scheduler` | 手动报告任务到期（`expire_at` 类型专用）。调用后标记任务为 completed，不再调度。**调用方**：04-任务执行引擎 的 `TaskContext` 中提供 `report_expire` 回调，任务图在执行完成（如 `ReturnHall` 前）时调用。09-运行控制中心 在构造 `TaskContext` 时注入此回调，闭包内调 `Scheduler.report_expire(task_name)`。若无人调用，`expire_at` 任务会无限期保留在调度表中 |
| `reset_fail_streak(task_name) -> None` | 🔓 公开 | `Scheduler` | 重置指定任务的 `fail_streak = 0`，清除 `skipped` 状态，将 `task_status` 恢复为 `waiting`。如果任务已熔断跳过，调用后重新加入调度。UI 面板上的"重置失败计数"按钮调此方法 |
| `check_daily_reset() -> None` | 🔒 私有 | `Scheduler` | 惰性检查是否跨日，若是则触发重置 |

**RepeatRule（执行规则）**：

| 方法签名 | 可见性 | 所属类 | 作用 |
|---------|--------|--------|------|
| `get_initial_next_run() -> datetime` | 🔓 公开 | `RepeatRule` | 首次注册时计算初始 `next_run_time`（宽容解析） |
| `calc_next_run() -> datetime` | 🔓 公开 | `RepeatRule` | 执行成功后计算下一次执行时间。**严格推进**：计算结果**必须大于当前时间**。例如 `daily` 任务若当前已过 `time_end`，推进后应为次日 `time_start`；`weekly` 任务若当前已过本周匹配日，推进到下周；`interval_days`/`interval_hours` 在跨越时间窗口边界时自动调整到下一个有效窗口起点。所有类型都需保证 `calc_next_run() > now`，避免推进后仍处于过期状态 |
| `is_expired(now) -> bool` | 🔓 公开 | `RepeatRule` | `once` 类型是否已完成 |

**TaskStateStore（执行记录持久化）**：

| 方法签名 | 可见性 | 所属类 | 作用 |
|---------|--------|--------|------|
| `load() -> dict[str, TaskState]` | 🔓 公开 | `TaskStateStore` | 从磁盘加载执行记录 |
| `save() -> None` | 🔓 公开 | `TaskStateStore` | 原子写盘（`tempfile + shutil.move`） |
| `get(task_name) -> TaskState \| None` | 🔓 公开 | `TaskStateStore` | 获取单个任务状态 |
| `get_or_create(task_name) -> TaskState` | 🔓 公开 | `TaskStateStore` | 获取或创建任务状态 |
| `update(task_name, **kwargs) -> None` | 🔓 公开 | `TaskStateStore` | 更新任务状态字段 |

### 5.4 核心流程

**get_next_task 调用链路**：
```
ScriptWorker 调 get_next_task()
  → 内部调 build_schedule()
  → [获取 _lock]
  →   check_daily_reset() → 跨日则重置 today_count（持锁执行，避免 DAILY_RESET 与 mark_done 交错）
  →   遍历 _tasks 所有启用任务
  →   对每个任务：
        is_due() → 三重判据
        check_times_limit() → today_count < max_daily?
  →   过滤 → 按 priority 升序 → 同优先级按 category 排序
  → [释放 _lock]
  → 发布 SCHEDULE_UPDATED 事件（已无锁）
  → 返回第一个任务名（Optional[str]）
```

**mark_done 推进链路**：
```
ScriptWorker 调 mark_done(name, success=True)
  → success=True:
      fail_streak 归零
      按 RepeatRule.type 推进 next_run_time
      today_count += 1
  → success=False:
      fail_streak += 1
      next_run = now + min(fail_streak × 5min, 60min)
  → save_state() 持久化
```

### 5.5 关键设计

- **next_run_time 核心判据**：解决"做过不再重复做"的问题，重启不丢失
- **三重判据**：`next_run_time` + `time_start/time_end` + `active_range`，精确控制"何时可做"
- **失败不推进 + 递增冷却 + 熔断**：防止死循环，`max_fail_streak` 达阈值后跳过任务。熔断分两类：`fail_streak`（可自动恢复）和 `unrecoverable`（必须手动重置）
- **原子持久化**：`tempfile + shutil.move`，崩溃不损坏
- **惰性每日重置**：在 `build_schedule()` 时检查跨日，无需独立定时器
- **活动日历导入**：批量管理限时活动，自动创建/更新/禁用任务
- **触发式任务（`trigger`）**：无时间配置、无初始 `next_run_time`，到期由外部触发驱动（手动 `update_next_run(name, now)` / 02-TriggerWatcher 发布 `trigger_detected` → 内部 `update_next_run`）。执行成功后 `mark_done` 标记 completed + 清空 next_run，进入已失效区标注"等待下次触发"；`load_state()` 重启不自动激活（区别于 `on_enter`）。`get_invalid_tasks()` 对 trigger 任务返回 reason="等待下次触发"
- **时区统一**：所有时间基于 UTC+8，配置中的 time_start/time_end 均为服务器本地时间
- **线程安全**：`_lock` 保护 `_next_run` 和 `_today_count` 的并发读写
