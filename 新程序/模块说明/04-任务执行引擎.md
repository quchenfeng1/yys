# 04-任务执行引擎（Task Execution Engine）

> **类型**：核心运行层  ｜  **对应说明书**：BaseTask 9.1 + DungeonTask 6.4  ｜  **对应用户模块**：#2 任务模块

---

## 一、目的与作用

**一句话定位**：将任务拆解为"特化模块+通用模块"的组合，通过任务步骤图（DAG）描述执行流程，支持顺序/条件分支/循环/错误恢复。

**核心职责**：
1. **任务步骤化**：每个任务由多个步骤组成，步骤分特化（副本独有）和通用（全项目复用）
2. **步骤图引擎**：用有向图描述步骤间关系，支持顺序/分支/循环/跳转
3. **错误恢复**：步骤失败时自动走错误恢复分支（返回大厅→跳过任务），不崩溃
4. **可中断执行**：步骤边界检查停止信号，响应外部中断请求
5. **自动注册**：任务文件放入 tasks/ 目录即自动发现注册，无需改代码

**设计原则**：
- **组合优于继承**：任务不是一个大类，而是多个步骤的组合
- **通用模块复用**：战斗循环、结算领奖、返回庭院等步骤全项目共享
- **特化模块最小化**：每个副本只写自己独有的界面操作
- **步骤图声明式**：执行流程用图描述，而非代码里的 if/for 嵌套
- **步骤边界可中断**：步骤内部原子执行不中断，但步骤间检查停止信号，快速响应停止/超时

## 二、模块属性与依赖

> 本节从程序实现角度定义所有属性。本模块包含多个类：BaseTask、TaskGraph、TaskStep、TaskRegistry。

### 2.1 依赖注入（外部模块引用）

任务执行引擎的类不直接持有外部模块引用，而是通过 TaskContext 在执行时传入。但模块整体依赖以下外部模块：

| 属性名 | 类型 | 作用域 | 作用 |
|--------|------|--------|------|
| `_config` | `ConfigManager` | 🔒 私有 | 读取任务配置（times/team_id/floor 等） |
| `_event_bus` | `EventBus` | 🔒 私有 | 发布 step_done / task_started / task_done 事件 |
| `_state_manager` | `StateManager` | 🔒 私有 | 更新 current_task / current_step / task_progress |
| `_registry` | `TaskRegistry` | 🔒 私有 | 管理任务注册与发现（`tasks/registry.py` 的 `discover_tasks()` 函数） |

> TaskContext 中的 executor 和 recognizer 由运行控制中心在调用 execute() 时注入，非本模块的固定依赖。

### 2.2 对外暴露属性（其他模块可读取）

通过状态管理模块间接读取。

| 属性名 | 类型 | 作用域 | 所属类 | 说明 |
|--------|------|--------|--------|------|
| `current_task` | `str \| None` | 📖 只读对外 | `TaskGraph` | 当前执行的任务名 |
| `current_step` | `str \| None` | 📖 只读对外 | `TaskGraph` | 当前执行的步骤名 |
| `task_progress` | `str \| None` | 📖 只读对外 | `TaskGraph` | 当前进度（如 "15/30"） |
| `task_result` | `TaskStatus` | 📖 只读对外 | `BaseTask` | 任务最终结果，execute() 返回值 |
| `step_result` | `StepStatus` | 📖 只读对外 | `TaskGraph` | 步骤执行结果，每步执行后更新 |

### 2.3 内部私有属性

**TaskGraph**（步骤图引擎）：

| 属性名 | 类型 | 作用 |
|--------|------|------|
| `_steps` | `dict[str, TaskStep]` | 步骤注册表：步骤名 → TaskStep 实例 |
| `_edges` | `dict[str, list[Edge]]` | 边表：步骤名 → 后续步骤列表（含跳转条件和错误分支） |
| `_entry` | `str` | 入口步骤名，execute 从该步骤开始 |
| `_task_name` | `str` | 当前执行的任务名（用于日志和状态推送） |
| `_fail_streak` | `int` | 当前任务连续失败计数，在 `_handle_error()` 中递增，达 `max_fail_streak`（默认 5）时熔断跳过任务 |
| `_max_fail_streak` | `int` | 熔断阈值，默认 5。可在任务配置中覆盖（`task_config.max_fail_streak`） |

**TaskStep**（步骤基类）：

| 属性名 | 类型 | 作用 |
|--------|------|------|
| `name` | `str` | 步骤名（唯一标识，调试用） |
| `is_generic` | `bool` | 是否通用模块。True=可跨任务复用，False=特化模块 |
| `retry_count` | `int` | 失败重试次数（默认0） |
| `timeout` | `float` | 单步超时秒数（默认120） |

**TaskRegistry（自动注册中心）**：

> **统一注册路径**：所有任务统一通过 `TaskRegistry` 注册和发现。`registry.py` 中的 `discover_tasks()` 函数启动时扫描 `tasks/` 下所有子目录的 `.py` 文件（排除 `__init__.py` 和 `base/`、`common/`），依次 `importlib.import_module` 导入并检查是否为 `BaseTask` 子类，自动调用 `register()` 注册。ScriptWorker 通过 `TaskRegistry.get(name)` 获取任务实例，不再直接 importlib。
>
> **实例化策略**：`TaskRegistry.get(name)` 每次调用返回**新的任务实例**（调用 `cls()` 构造），而非缓存单例。这确保多次执行同一任务时状态不会混染（每次 `execute()` 都构造新 `TaskGraph`）。`get_all()` 和 `list_by_category()` 同理返回新实例列表。

| 属性名 | 类型 | 作用 |
|--------|------|------|
| `_tasks` | `dict[str, type[BaseTask]]` | 任务名 → 任务类的映射 |
| `_categories` | `dict[str, list[str]]` | 分类名(daily/permanent/event/special) → 任务名列表 |

## 三、运行逻辑

### 3.1 步骤图执行流程

步骤图引擎在**步骤边界**检查停止信号，步骤内部保持原子执行：

```
步骤图开始执行（接收到 context，含 stop_event 和 timeout）
  → 记录任务开始时间
  → 从入口步骤开始循环：

  步骤循环开始：
    ├── [步骤边界] 检查 stop_event 是否被设置
    │   ├── 已设置 → 走中断收尾 → 返回 TaskResult(status="aborted")
    │   └── 未设置 → 继续
    ├── [步骤边界] 检查是否超时（当前时间 - 开始时间 > timeout）
    │   ├── 已超时 → 走中断收尾 → 返回 TaskResult(status="timeout")
    │   └── 未超时 → 继续
    ├── 执行当前步骤的 execute(context) → 得到 StepResult
    ├── 发布 step_done 事件（含步骤名和结果）
    ├── 判断 StepResult.status：
    │   success → 按寻边规则确定下一步
    │   fail    → _handle_error(context) 错误恢复
    │              ├── 恢复成功 → 重试当前步骤
    │              └── 恢复失败 → fail_streak++ → 超过上限则跳过任务
    │   skip    → 按条件边跳到指定步骤
    │   retry   → 重新执行当前步骤（重试计数已在 _execute_step 内处理）
    └── 回到步骤循环开始

  → 所有步骤完成 → 返回 TaskResult(status="success")
```

> **BattleLoop 循环机制**：`BattleLoop` 是一个单步，但它在内部通过 `check_interrupt()` 做循环：每次战斗结束后检查剩余次数，若未完成则调用 `context.recognizer.wait()` 等待下一场战斗开始，而非通过图回环。因此整个战斗循环在图层面只占一个步骤，步骤内部的循环逻辑由步骤自身实现。`BattleLoop.step.retry_count` 控制的是单场战斗的重试次数，而非总循环次数。总循环次数由 `task_config.loop_count` 控制，运行时进度通过 `context.state["battle_loop.completed"]` 更新。**此模式适用于所有需要内部循环的步骤**。
>
> **任务级超时与步内循环**：`context.timeout`（默认 300s）仅在步骤边界检查，不会自动传入 BattleLoop 内部。因此 BattleLoop 等长循环步骤**必须自行在循环体内检查任务级超时**——每次战斗结束后检查 `time.time() - context.start_time > context.timeout`，超时则跳出循环并返回 `StepResult(status="success")` 以正常路径结束任务。否则，步内循环可能无限持续到手动停止。
>
> **哪些步骤属于"长循环步骤"**：
> - `BattleLoop`：战斗循环，每次战斗后检查剩余次数和超时
> - `CoopPassive`：组队待机，等待战斗结束期间应定期检查超时（例如每次识图轮询后检查）
> - 其他包含 `while` / `for` 内部循环的步骤
>
> 长循环步骤在以下关键等待点**必须**检查 `context.timeout` 并做出响应：
> 1. 每次循环迭代开始时
> 2. 每次 `context.recognizer.wait()` / `wait_any()` 返回后
> 3. 每次战斗/操作结束后，更新进度前

### 3.2 步骤分类

**通用模块**（全项目复用）：

| 通用模块 | 功能 | 复用场景 |
|----------|------|----------|
| BattleLoop | 战斗循环：等待结束→检测胜负→结算；支持运行时进度恢复（从 `task_runtime_progress` 读取剩余次数） | 所有有战斗的副本 |
| ClaimReward | 领取奖励：点击结算→确认→关弹窗 | 所有副本结算后 |
| ReturnHall | 返回庭院：点返回→确认退出→等加载 | 所有任务收尾 |
| PreCheckTeam | 阵容检查：验证当前阵容→不匹配则修正 | 所有战斗任务进战前 |
| SelectTeam | 选阵容：界面→选中→锁定 | 所有战斗任务进战时 |
| ErrorReturn | 错误恢复：识别失败→返回大厅→标记跳过 | 所有任务的错误分支 |
| CheckStamina | 体力检查：体力不足则跳过 | 所有消耗体力的副本 |
| ClosePopup | 关弹窗：检测并关闭通用弹窗 | 任意步骤间 |
| **CoopHost** | **组队主机**：创建队伍→邀请→等待加入→开战（谁开队谁执行） | 需要组队的战斗副本 |
| **CoopJoin** | **组队成员**：接收邀请→加入队伍→准备就绪 | 需要组队的战斗副本 |
| **CoopPassive** | **组队待机**：加入队伍后不操作，等待战斗结束自动领奖（模式B：小号开车时主号用） | 被带的一方 |
| **FragmentExchange** | **碎片交换**：进入好友界面→发起/接受碎片请求→确认 | 碎片交换任务 |

**特化模块**（副本独有）：每个副本只编写特有的入口操作，如进入副本、选择层数等。

### 3.3 任务组合示例

```
御魂副本任务 = EnterYuhun(特化) → CheckStamina(通用) → PreCheckTeam(通用)
             → SelectTeam(通用) → BattleLoop(通用, 循环N次)
             → ClaimReward(通用) → ReturnHall(通用)
             [任何步骤失败] → ErrorReturn(通用)
             [中断恢复] BattleLoop 从 task_runtime_progress 读取剩余次数

每日签到任务 = SignInEntry(特化) → ClaimReward(通用) → ReturnHall(通用)
             [失败] → ErrorReturn(通用)
```

> **运行时进度恢复**：当任务因用户停止或异常中断后重新启动时，BattleLoop 检查 `task_runtime_progress` 中该任务的 `completed` 值，从剩余次数开始执行。任务配置文件中的 `loop_count` 不变，进度独立存储于 `07-运行时状态管理` 的 `task_runtime_progress` 键中。
>
> **`context.state` → `task_runtime_progress` 同步规则**：
> ```
> 写入（步骤内部，由 BattleLoop 等循环步骤执行）：
>   → 每次战斗结束后 context.state["battle_loop.completed"] += 1
>   → 步骤通过 context.executor 间接调用 07.set_state("task_runtime_progress", ...)
>     写入时以 {context.task_name: {completed, total, updated, loop_type}} 格式合并更新
>
> 持久化（09-运行控制中心 在停止时执行）：
>   → 用户点停止 / 任务完成 / 异常中断
>   → 09 读取 07.get_state("task_runtime_progress")
>   → json.dump → config/runtime/task_runtime_progress.json
>
> 恢复（09-运行控制中心 在启动时执行）：
>   → 启动时 09 读取 task_runtime_progress.json
>   → 07.set_state("task_runtime_progress", loaded_data)
>   → BattleLoop 启动时通过 context.state 读取已完成次数
>     读取优先级：context.state["battle_loop.completed"] > task_runtime_progress
>     即内存中的 state 优先于磁盘持久化数据（处理同一任务多次执行间的状态累积）
> ```

### 3.4 中断与超时机制（与运行控制中心的協作）

任务执行引擎通过 TaskContext 接收来自运行控制中心的停止信号和超时设定，在步骤边界做出响应：

**停止响应流程**：
```
运行控制中心用户点击停止
  → 设置 context.stop_event
  → 步骤图引擎在当前步骤完成后检查到 stop_event
  → 停止执行后续步骤，跳过剩余步骤
  → 执行收尾（如返回庭院）
  → 返回 TaskResult(status="aborted")
```

**超时响应流程**：
```
运行控制中心执行线程创建任务子线程时设定超时（如300秒）
  → context.timeout = 300
  → 步骤图引擎每执行完一个步骤检查耗时
  → 超时 → 停止执行后续步骤
  → 返回 TaskResult(status="timeout")
```

**关键规则**：
- **步骤内不中断**：正在执行的步骤（如等待战斗结果）不受 stop_event 影响，保持原子性
- **步骤边界响应**：stop_event 和超时检查在每一步执行前和执行后进行
- **收尾保障**：即使被中断，也会执行 ErrorReturn 等清理步骤

## 四、重点功能

### 4.1 步骤图引擎

用有向图描述任务流程，支持顺序执行、条件分支、循环、任意跳转。步骤执行结果决定下一步走向，失败自动走错误恢复路径，避免任务崩溃。

### 4.2 通用模块复用体系

将战斗、领奖、返回等高频操作抽象为通用模块，所有任务共享。新增副本时只需编写特化入口步骤，其余步骤从通用模块库中组合。

### 4.3 自动注册机制

任务文件放入 tasks/ 对应分类目录即被自动发现注册，无需手动维护任务列表。支持 daily / permanent / event / special 四类任务分类。

### 4.4 步骤级状态推送

每执行完一个步骤即通过事件总线发布进度事件，UI 可实时展示当前执行到哪一步。

### 4.5 步骤边界可中断

每个步骤原子执行不中断，但步骤间检查停止信号和超时。兼顾了**步骤完整性**（不会出现半执行的步骤）和**快速响应**（用户点停止后最多等待一个步骤的完成时间）。

### 4.6 统一任务结果（TaskResult）

`task.execute()` 返回统一的 TaskResult，包含 status（success/fail/timeout/aborted）和 reason。运行控制中心据此决定如何推进调度或恢复。

### 4.7 阶梯式错误恢复与熔断

步骤失败时不直接放弃，而是：①截图保存现场（通过 `context.executor.screenshot()`）→ ②`context.executor.detect_scene()` 分析当前页面 → ③根据场景选择恢复路径（庭院→重试、战斗中→等待结算、弹窗→关闭、未知→保护模式） → ④恢复成功则重试、恢复失败则递增 `_fail_streak`。连续失败达 5 次后熔断跳过任务，防止死循环。**所有恢复操作均通过 `context.executor` 执行**，确保安全注入（防封偏移、可打断等待）不被绕过。

### 4.8 步骤内循环模式

`BattleLoop` 等需要重复执行的步骤采用"步骤内循环"模式：步骤自身通过 `check_interrupt()` 在循环体内检查停止信号，使用 `context.state` 记录进度。图层面只看到一个步骤，简化了图的拓扑结构。

### 5.1 模块结构

```

### 5.2 核心数据结构

模块内部的核心数据类定义。

**Edge（步骤边）**：
| 字段 | 类型 | 说明 |
|------|------|------|
| `to_step` | `str` | 目标步骤名 |
| `edge_type` | `EdgeType` 枚举 | `normal`（默认成功后续）/ `error`（失败恢复）/ `skip`（跳过跳转）/ `conditional`（条件分支） |
| `condition` | `callable \| None` | 条件函数：`(context, StepResult) -> bool`，仅 `conditional` 类型使用。返回 True 则走此边 |

> **寻边规则**：`run()` 中确定下一步时，优先匹配 `StepResult.next_step`（显式指定）；若为 None，则依次检查当前步骤的所有出边：`conditional` 边评估 condition 函数、`skip` 边检查 StepResult.status==skip、`error` 边检查 status==fail、`normal` 边作为默认 fallback。若无可匹配边，任务结束返回 success。

**TaskResult**（`task.execute()` 的统一返回值）：
| 字段 | 类型 | 说明 |
|------|------|------|
| `status` | `TaskStatus` 枚举 | `success` / `fail` / `timeout` / `aborted` |
| `reason` | `str` | 失败/超时/中断的原因描述 |
| `data` | `dict \| None` | 可选附加数据 |

**StepResult**（`step.execute()` 的返回值）：
| 字段 | 类型 | 说明 |
|------|------|------|
| `status` | `StepStatus` 枚举 | `success` / `fail` / `skip` / `retry` |
| `next_step` | `str \| None` | 显式指定下一步（条件跳转时用） |
| `data` | `dict \| None` | 输出数据，传给后续步骤 |
| `message` | `str` | 日志消息 |

**TaskContext**（步骤间共享上下文，由运行控制中心构造注入）：
| 字段 | 类型 | 提供方 | 说明 |
|------|------|--------|------|

### 5.4 核心流程

**任务执行链路（被运行控制中心调用）**：
```
运行控制中心执行线程
  → 构造 TaskContext（stop_event + timeout + executor + ...）
  → 调用 task.execute(context)
     → BaseTask.execute()
        → self._build_graph() → 获取子类定义的 TaskGraph
        → graph.run(context)
           → 步骤循环（每步前检查中断）
           → 返回 TaskResult
     ← 返回 TaskResult
  → 根据 TaskResult.status 决定后续
```

**_execute_step 内部逻辑**：
```
传入步骤和 context
  → 根据 step.retry_count 确定重试次数
  → 循环执行：
      调用 step.execute(context)
      成功 → 返回 StepResult(status="success")
      失败 → 未达重试上限 → 等待 + 重试
      失败 → 已达重试上限 → 返回 StepResult(status="fail")
  → 步骤执行异常 → 调用 step.cleanup(context) → 重新抛出
```

**_handle_error 内部逻辑**（错误场景分析 + 阶梯式恢复 + 熔断）：
```
传入 context（含当前步骤名和执行异常/失败原因）
  → 任务连续失败计数器 _fail_streak += 1
  → 判断 _fail_streak：
      ├── ≥ max_fail_streak（默认 5）→ 熔断：返回 StepResult(skip)，跳过此任务
      │    （标记任务为"连续失败跳过"，由运行控制中心决定是否冷却后再试）
      └── < max_fail_streak → 执行恢复：
            → 通过 context.executor.screenshot() 获取当前截图
            → 通过 context.executor.detect_scene(candidates) 分析当前页面
            ├── 匹配到已知场景 → 按场景选择恢复操作
            │    courtyard（庭院）→ 直接重试
            │    battle（战斗中）→ context.executor.wait_any(["victory","defeat"])
            │                      → context.executor.click_image("confirm")
            │                      → context.executor.ensure_scene("courtyard")
            │    popup（弹窗）→ context.executor.click_if_exists("close_btn")
            │    login（登录）→ 游戏断开 → 标记不可恢复
            └── 未匹配（未知场景）→ 保护模式：
                  → 通用退出序列（全部通过 context.executor 调用）：
                    step 1: context.executor.click_if_exists("close_btn")
                    step 2: context.executor.input_key("BACK")  
                    step 3: context.executor.ensure_scene("courtyard", timeout=5)
                  → 任一 step 返回 True → 继续下一步
                  → 三步全 False → 标记不可恢复
            → 恢复成功 → _fail_streak 不变（保持计数）→ 返回 StepResult(retry)
            → 恢复失败 → _fail_streak 保持 → 返回 StepResult(fail)
```

> **调用路径说明**：`_handle_error()` 是 `TaskGraph` 的私有方法，不直接持有任何外部模块引用。所有设备操作（截图、识图、点击、按键）均通过 `context.executor`（14-执行器模块）间接执行。`detect_scene()` 是 `Executor` 的公开方法（14-执行器模块 §5.2 定义），参数为候选场景模板名列表，返回最先匹配的场景名。此路径确保错误恢复不绕开执行器的安全注入（防封偏移+可打断等待）。
>
> **前置依赖**：`_handle_error()` 的正确工作依赖于以下条件在实现时被满足：
> 1. **14-执行器模块** 必须定义 `detect_scene(candidates) -> str | None` 方法
> 2. **02-图像识别模块** 的素材目录中必须有 `courtyard`（庭院）、`battle`（战斗中）、`popup`（弹窗）、`login`（登录）等场景的模板图
> 3. 保护模式中的通用退出序列依赖于 `close_btn` 模板的存在。若这些模板缺失，`_handle_error()` 的阶梯恢复将降级为保护模式或直接标记不可恢复

> **熔断机制**：`_fail_streak` 在任务开始执行时初始化为 0，仅在 `_handle_error` 中递增。当达到 `max_fail_streak`（默认 5）时熔断，跳过此任务返回 `TaskResult(status="fail", reason="连续失败熔断")`。此计数器**不**在成功时自动清零——只有运行控制中心手动重置或脚本重启后才会清零。这是为了防止"成功一次掩盖了之前大量失败"的问题。
>
> **熔断后处理（09-运行控制中心 的职责）**：运行控制中心收到熔断返回的 `TaskResult(status="fail", reason="连续失败熔断")` 后，应**将该任务标记为 `skipped` 并应用冷却时间**（如 10 分钟），而非直接移出队列。冷却结束后再由填充线程重新入队。此行为在 09 模块的设计书中定义，04 模块不负责重试决策。
>
> **`context.state` 的状态来源**：任务首次启动时，`context.state` 的初始数据来自 09-运行控制中心 加载的 `task_runtime_progress.json`（通过 07 状态管理注入）。09 在构造 `TaskContext` 时必须执行一次 `task_runtime_progress = state_manager.get_state("task_runtime_progress")` 并注入到 `context.state` 中。若 09 忘记加载磁盘数据，`context.state` 为空，内存优先规则将导致进度丢失。因此**09 模块必须保证启动时加载磁盘进度并写入 state**。
>
> **`context.state` 的线程安全**：步骤图中的步骤按顺序单线程执行，`context.state` 的读写天然串行（同一时刻只有一个步骤在读写），因此不需要额外加锁。此约定前提是：运行控制中心确保同一 `TaskContext` 不会被多线程并发访问。

### 5.5 关键设计

- **步骤边界可中断**：步骤内部原子执行不中断，步骤间检查 stop_event 和超时
- **TaskResult 统一返回值**：运行控制中心根据 status（success/fail/timeout/aborted）决定如何推进调度
- **步骤原子性**：保证每个步骤要么完整执行完，要么完全不执行（不会半截中断）
- **步骤内循环模式**：`BattleLoop` 等需要循环的步骤通过 `check_interrupt()` 在内部实现循环，且**必须自行检查 `context.timeout`**（任务级超时不传入步内循环），而非图回环。图层面只看到一个步骤，简化图结构
- **Edge 条件寻边**：基于 EdgeType 的条件评估确定下一步，`StepResult.next_step` 可显式覆盖
- **阶梯式错误恢复**：`_handle_error()` 根据场景检测结果选择恢复路径，非一刀切的重试
- **熔断保护**：连续失败达 `max_fail_streak`（默认 5）后跳过任务，防止死循环
- **运行时进度恢复**：`context.state["battle_loop.completed"]` 通过 07 持久化到 `task_runtime_progress.json`。同步规则：写入按 `{task_name: {completed, total, updated}}` 格式合并；恢复时内存 state 优先于磁盘数据
- **TaskRegistry 每次返回新实例**：`get(name)` / `get_all()` / `list_by_category()` 每次调用都构造新 `BaseTask` 实例，确保多次执行同一任务时状态隔离。`_tasks` 存储的是任务类而非实例。若任务调度极频繁（如每分钟调 N 次），频繁构造/析构可能对 Python GC 产生压力——当前设计对此不做特殊优化（绝大多数场景无影响），未来可按需引入对象池
- **state 键完全限定**：约定使用 `{task_name}.{step_name}.{key}` 格式（如 `yuhun.battle_loop.completed`），避免同一步骤在多任务或多处复用时键碰撞
- **统一注册路径**：所有任务通过 `TaskRegistry.discover_tasks()` 扫描发现，ScriptWorker 通过 `get(name)` 获取，不绕行
- **TaskContext 依赖注入**：executor/recognizer/stop_event 等由运行控制中心在 execute() 时注入，TaskGraph 自身不持有外部模块引用
