# 09-运行控制中心（Run Control Center）v4.0

> **类型**：核心运行层 ｜  **对应说明书**：5.9 ｜  **说明**：三线程持续调度（ScriptWorker 统一实现）
>
> **实现架构**：本模块的核心运行控制逻辑实现在 **`RunController`**（`core/run_controller.py`）中，为纯 Python 实现，不依赖 Qt。**`ScriptWorker`**（`ui/script_worker.py`）继承 `QThread`，封装 RunController 并添加 pyqtSignal 通信，使三线程模型（填充+执行+扫描）与 Qt 事件循环兼容。ScriptWorker 本质上是一个 Qt 适配层，核心逻辑在 RunController 中。
> 本设计文档中的「RunController」即指代运行控制逻辑。

---

## 一、目的与作用

**一句话定位**：脚本运行时生命周期管理。三线程模型（填充 + 执行 + 扫描）持续驱动任务调度。

**核心职责**：
1. **三线程调度**：填充线程到期任务入队、执行线程 FIFO 出队执行、扫描线程小号维护
2. **场景检测与弹窗拦截**：每步执行前扫描弹窗并自动关闭
3. **错误恢复机制**：任务失败后场景分析 → 恢复路径选择 → 保护模式
4. **暂停/恢复控制**：响应 UI 暂停/恢复信号，暂停时停止调度但保留现场，恢复后继续执行
5. **组队协调**：协调主号与小号之间的组队操作，通过事件驱动切换账号和执行组队动作
6. **定时启停**：支持 `scheduled_start` / `scheduled_stop` / `run_window` 配置
7. **运行时进度持久化**：停止保存 `task_runtime_progress.json`，启动恢复
8. **自适应休眠**：无任务时递增休眠（2~10s），减少 CPU 空转

**设计原则**：
- **三线程协同**：填充线程不阻塞执行，执行线程专注任务，扫描线程独立维护
- **协作停止**：`threading.Event` 信号 + daemon 线程，兼容 macOS/Linux/Windows
- **错误自愈**：失败自动进入恢复流程（场景分析→恢复路径），单任务最多重试 3 次，全部失败则跳过，避免死循环
- **暂停不中断**：暂停时保留全部线程和队列状态，恢复后继续执行，无需重新初始化
- **事件驱动组队**：组队协调通过事件总线通信，09 不直接操作小号设备，保持职责解耦
- **状态联播**：通过事件总线广播启停/任务状态，UI 实时刷新

| 属性名 | 类型 | 作用域 | 说明 |
|--------|------|--------|------|

| `current_task` | `str \| None` | 📖 只读对外 | 当前执行的任务名 |

### 2.3 内部私有属性

| 属性名 | 类型 | 作用 |
|--------|------|------|
| `_stop_event` | `threading.Event` | 停止信号。被设置时所有线程退出循环 |
| `_task_queue` | `deque[str]` | FIFO 任务队列（填充线程入队 `append`，执行线程出队 `popleft` O(1)） |
| `_queue_lock` | `threading.Lock` | 保护 `_task_queue` 的线程安全锁。注意：`deque` 的 `append`/`popleft` 在 CPython 中因 GIL 单次操作原子，但先 `len()` 后 `popleft()` 的两步操作之间仍有竞态窗口，必须用 `with _queue_lock:` 包裹完整检查+出队 |
| `_queue_not_empty` | `threading.Condition` | 可选的队列非空通知条件变量。填充线程入队后 `notify()`，执行线程在 `popleft` 队列空时 `wait(timeout=0.5)` 替代固定休眠，减少空转延迟 |
| `_state` | `RunState` | 当前运行状态，通过 `_state_lock` 保护读写 |
| `_state_lock` | `threading.Lock` | 保护 `_state` 的读写线程安全 |
| `_recover_count` | `dict[str, int]` | 各任务连续恢复失败计数（仅执行线程访问，无需锁） |
| `_idle_counter` | `int` | 空闲计数器，用于自适应休眠（仅填充线程访问，无需锁） |
| `_scanner_lock` | `threading.Lock` | 扫描线程互斥锁（non-blocking acquire），防止与执行线程同时操作设备 |
| `_scanner_running` | `threading.Event` | 扫描线程运行中标志。扫描开始时 set，结束时 clear。执行线程在开始任务前检查，若扫描中则等待 |
| `_trigger_watcher` | `TriggerWatcher` | 触发监控子服务（构造时创建，运行期启停）。监控触发式任务（`repeat.type=trigger`）识别列表，命中 → 发布 `trigger_detected` → 05 置为到期入队 |

## 三、运行逻辑

### 3.1 整体流程

三线程协同工作模型：

```
RunController 启动（_on_start → _start_run）
  │
  ├── 1. 加载配置 → build_schedule()
  ├── 2. 恢复运行时进度（task_runtime_progress.json）
  ├── 3. 清空任务队列
  └── 4. 启动触发监控 → _trigger_watcher.start()
  │        （收集 trigger 任务识别列表 → 常驻监控线程）
  └── 5. 同时启动三个线程：
        │
        ├── ① _filler_loop()    — 填充线程↙
        │     while not stop:
        │       定时启停检查 → run_window 检查
        │       build_schedule() → get_next_task()
        │       有到期任务？→ 入队 _task_queue
        │       无任务？→ adaptive_delay() 自适应休眠
        │
        ├── ② _executor_loop()  — 执行线程↘
        │     while not stop:
        │       _task_queue 出队
        │       弹窗扫描（_scan_popups_before_exec）
        │       执行任务（含错误恢复：_execute_task_with_recovery）
        │       mark_done() + 更新运行时进度
        │
        └── ③ _scanner_loop()   — 扫描线程（可选）
              while not stop:
                遍历全部小号
                更新 sub_account_status
                执行维护操作（收邮件/查协作）
                分析 findings → 更新 best_finding
                休眠（默认 30 分钟，分段等待停止信号）

  停止（stop）
    └── _stop_event.set()
    └── 停止触发监控 → _trigger_watcher.stop()
    └── 等待三线程退出（join timeout=3）
    └── 保存运行时进度（_save_runtime_progress）
    └── 清理状态 → 发布 "run_stopped"
```

**执行线程的单次任务执行流程**：

```
_execute_task_with_recovery(task_name)
  │
  ├── 尝试执行（最多 3 次）
  │     ├── _execute_task_once(task_name)
  │     │   └── registry.get(task_name).execute()
  │     │
  │     └── 失败？→ _error_recovery()
  │           ├── 截图保存现场
  │           ├── detect_scene(candidates) 分析当前页面
  │           ├── 根据场景选择恢复路径：
  │           │   战斗结算 → 点击确认
  │           │   战斗失败 → 退出 → 回庭院
  │           │   弹窗干扰 → close_btn
  │           │   登录界面 → 终止任务
  │           │   未知场景 → 保护模式（通用退出序列）
  │           └── 恢复成功 → 重试 / 恢复失败 → 跳过任务
  │
  └── 返回 success
```

### 3.2 扫描线程（小号维护）

独立于主执行循环的第三个线程，负责定时遍历全部小号执行维护操作：

```
扫描线程 _scanner_loop()
  │
  └── 循环（间隔可配置，默认每 30 分钟）：
        │
        ├── 1. 获取全部小号列表（15-账号管理.get_all_accounts）
        │     └── 初始化 sub_account_status：全置为 idle
        │
        ├── 2. 对每个小号：
        │     ├── 更新状态 → sub_status={sub_id: {status:"login"}}
        │     ├── 调 01-设备连接.switch_device(sub.device_id)
        │     ├── 更新状态 → {status:"scanning", task:"检查协作"}
        │     ├── 执行小号维护操作：
        │     │   ├── 收邮件 / 领奖励
        │     │   ├── 查看协作 → 若发现高价值协作则记录
        │     │   ├── 查看商店 → 若发现高价值商品则记录
        │     │   └── 其他简单日常
        │     ├── 更新状态 → {status:"idle", task:"等待"}
        │     └── 记录 findings 到 07.set_state("sub_account_findings")
        │
        ├── 3. 遍历完成后分析 findings：
        │     ├── 对比全部小号的协作/商品
        │     ├── 选出最优结果 → 07.set_state("best_finding")
        │     ├── 更新 sub_status → {sub_id: {status:"teaming", task:"分享给大号"}}
        │     └── 登录该小号 → 通过 `_executor` 操作分享给大号（识图打开好友界面、选择大号、发送请求）
        │
        └── 4. 全部完成 → sub_account_status 全回归 idle

> **线程安全**：扫描线程与执行线程**共享同一个物理设备**（模拟器实例），不能同时操作。采用双层互斥保护：
>
> **第一层（条件预判）**：扫描线程仅在以下条件**全部满足**时尝试运行：
> 1. 执行线程当前**无任务执行中**（`_task_queue` 为空，`current_task` 为 None）
> 2. 填充线程处于**长等待期**（`adaptive_delay` > 5s）
> 3. 距离上次扫描已超过**最小间隔**（默认 30 分钟）
>
> **第二层（运行时互斥）**：
> - 扫描开始前 `_scanner_lock.acquire(blocking=False)`，获取失败则跳过本轮
> - 扫描开始时设置 `_scanner_running`（`threading.Event`），扫描结束时清除
> - 执行线程在 `_task_queue` 出队后、实际执行前检查 `_scanner_running.is_set()`：若扫描正在运行，等待 `_scanner_running.wait(timeout=5)` 或通知扫描线程提前中断
> - 执行线程入队新任务时若扫描正在运行，不强制中断扫描——扫描线程在当前小号操作完后检查 `_stop_event` 和谐退出
>
> 与 07 的交互通过 `set_state` 加锁保证。执行线程在组队时也会更新 sub_account_status（参与组队的小号置为 teaming），两线程通过 07 统一状态层同步，UI 面板实时刷新。
```



### 3.3 定时启停机制

```
启动时 → 读取配置中的 scheduled_start / scheduled_stop / run_window
  ├── scheduled_start 已设且当前时间未到
  │     → 不创建 ScriptWorker，由 MainWindow 的定时器周期性检查
  │     → 到达 scheduled_start 时由 MainWindow 创建 ScriptWorker 并启动
  │     （方案 A：无需专用等待线程，MainWindow 定时器复用 UI 刷新周期）
  │
  ├── run_window 已设且当前时间不在窗口内
  │     → 等待至窗口开启（避免深夜运行）
  │
  ├── scheduled_stop 已设且当前时间已过
  │     → 自动停止（防止超时运行）
  │
  └── 正常 → 继续执行

运行中 → 每轮循环检查
  ├── 超出 run_window → 暂停执行，等待窗口开启
  └── 超过 scheduled_stop → 自动停止
```

### 3.4 停止流程

```
用户点停止 → _on_stop() → RunController.stop()
  │
  ├── 1. _stop_event.set()                   # 设置停止标志
  ├── 2. 等待三线程退出（join timeout=3s）
  │     所有线程均为 daemon=True
  ├── 3. 保存运行时进度
  │     _save_runtime_progress()
  │     → 07.get_state("task_runtime_progress")
  │     → json.dump → config/runtime/task_runtime_progress.json
  ├── 4. scheduler.save_state()              # 保存调度状态
  ├── 5. 清理状态：清空队列、线程引用置 None
  ├── 6. 07.set_state("run_status", "stopped")
  └── 7. event_bus.publish("run_stopped", "09-运行控制中心")      # 通知 UI 恢复
```

> **跨平台兼容**：使用 `threading.Event` 协作停止 + daemon 线程，
> 不依赖 Windows TerminateThread API，兼容 macOS / Linux / Windows。

### 3.5 运行时进度恢复与持久化

```
启动时 → _restore_runtime_progress()
  ├── 读 config/runtime/task_runtime_progress.json（如存在）
  ├── 07.set_state("task_runtime_progress", loaded_data)
  └── 各任务启动时读取 completed 值

停止时 → _save_runtime_progress()
  ├── 07.get_state("task_runtime_progress")
  └── json.dump → config/runtime/task_runtime_progress.json
```

### 3.6 场景检测与弹窗拦截

执行线程在每次任务执行前调用 `_scan_popups_before_exec()`：

```
每步执行前 → _scan_popups_before_exec()
  ├── 遍历弹窗模板列表：
  │   common/popup/popup_reward
  │   common/popup/popup_ad
  │   common/popup/popup_update
  │   common/ui/close_btn
  ├── 对每个模板调 executor.click_if_exists()
  │   ├── 匹配到 → 点击关闭 → sleep(1) → 继续扫描
  │   └── 未匹配 → 跳过
  └── 全部检查完毕 → 开始执行任务
```

### 3.7 异常场景恢复机制

任务执行失败时 `_execute_task_with_recovery()` 自动进入恢复流程。注意执行层重试与调度层冷却的关系：
- 执行层（09）：同一次调度周期内的即时恢复，最多重试 3 次
- 调度层（05）：`mark_done(name, success)` 递增 `fail_streak` 并添加冷却
- **交互规则**：3 次重试中**任一次成功** → `mark_done(name, success=True)`（清零 fail_streak）；**全部失败** → `mark_done(name, success=False)`（递增 fail_streak + 冷却）。失败不推进 next_run_time，冷却防止死循环

任务执行失败时 `_execute_task_with_recovery()` 自动进入恢复流程：

```
任务失败（execute 返回 False / 抛出异常）
  │
  ├── 1. 截图保存现场 → event_bus.publish("error_occurred")
  │
  ├── 2. 分析当前页面 → executor.detect_scene(candidates)
  │     candidates = [
  │       "scenes/courtyard/courtyard_main",
  │       "scenes/login/enter_game",
  │       "common/popup/popup_reward",
  │       "common/battle/victory",
  │       "common/battle/defeat",
  │       "common/ui/close_btn",
  │     ]
  │     ├── 匹配到 → 07.last_known_scene = scene → 恢复路径
  │     └── 未匹配 → 保护模式
  │
  ├── 3. 恢复路径选择
  │     victory     → click_image("confirm_btn")
  │     defeat      → click_image("close_btn") → navigate_to_courtyard()
  │     popup/close → click_image("close_btn") → 重试
  │     login       → 游戏断开 → 终止任务 → 返回 False
  │     courtyard   → 已在庭院，直接重试
  │
  ├── 4. 恢复后验证
  │     ├── 恢复成功 → 重试执行（最多 3 次）
  │     └── 恢复失败 → 跳过任务
  │
  └── 5. 保护模式（未知场景）
        ├── click_image("close_btn") → 关弹窗
        ├── input_key("BACK")        → 返回键
        └── 任一成功且回到庭院 → True / 全失败 → 跳过任务
```

### 3.8 异常处理总表

| 异常场景 | 检测方式 | 恢复行为 | 资源保护 |
|---------|---------|---------|---------|
| 识图失败（click_image 返回 False） | 方法返回值 | `detect_scene` 分析页面 → 恢复路径 | 最多重试3次，若恢复成功则继续，全部失败则跳过任务 |
| 场景不匹配（ensure_scene 超时） | 方法返回值 | `detect_scene` 扫描候选 → 恢复导航 | 同上 |
| 战斗失败（任务步骤逻辑判断） | 任务业务逻辑 | `click_image("退出")` → `ensure_scene("庭院")` | 记失败次数，冷却递增 |
| 弹窗干扰 | 步骤前 `detect_scene` | `click_image("close_btn")` 关弹窗后重试 | 自动处理，不计失败 |
| 完全未知页面 | `detect_scene` 无匹配 | 通用退出序列 → 失败则跳过任务 | 跳过任务，保护资源 |
| 连接断开 | 心跳检测 | 终止当前任务 → 尝试重连 | 重连失败则停止 |
| 组队中断 | 组队操作返回 False 或超时 | 已切到小号 → 记录现场 → 切回主号 → 重试或跳过任务；未切到小号 → 直接重试 | 最多重试3次，全部失败则跳过 |
| 调度循环异常 | try/except | 递增错误计数 → 超过配置上限（`global.run.max_loop_errors`，默认10）自动停止 | 防止无限崩溃 |

### 3.9 暂停与恢复流程

用户点击暂停/恢复时，通过事件总线触发响应：

```
用户点击暂停 → 10-参数桥接模块.RunBridge.request_pause()
  → 发布 pause_requested 事件
  → 09-运行控制中心._on_pause()
      │
      ├── 1. 获取 _state_lock
      ├── 2. 对比当前状态：
      │     └── 非 RUNNING 状态 → 释放锁 → 忽略（仅 RUNNING 可暂停）
      ├── 3. 设置 _state = PAUSED
      ├── 4. 释放 _state_lock
      ├── 5. 07.set_state("run_status", "paused")
      ├── 6. event_bus.publish("run_paused", "09-运行控制中心")
      └── 7. 填充线程和执行线程在下一轮循环中检查 _state
            ├── _filler_loop：检测到 PAUSED → 进入等待循环（分段休眠，每段检查 _state）
            └── _executor_loop：检测到 PAUSED → 等待（分段休眠，每段检查 _state）

用户点击恢复 → 10-参数桥接模块.RunBridge.request_resume()
  → 发布 resume_requested 事件
  → 09-运行控制中心._on_resume()
      │
      ├── 1. 获取 _state_lock
      ├── 2. 对比当前状态：
      │     └── 非 PAUSED 状态 → 释放锁 → 忽略
      ├── 3. 设置 _state = RUNNING
      ├── 4. 释放 _state_lock
      ├── 5. 07.set_state("run_status", "running")
      ├── 6. event_bus.publish("run_resumed", "09-运行控制中心")  -- 恢复后通知 UI
      └── 7. 填充线程和执行线程检测到 RUNNING → 恢复正常循环
```

> **暂停期间的行为**：填充线程停止入队新任务，执行线程完成当前正在执行的任务后进入等待，不再取出新任务。扫描线程不受暂停影响（小号维护独立于主执行循环）。`_state` 的检查通过分段休眠（每段 1s 检查一次 `_state`）实现，确保恢复后最迟 1 秒内响应。

### 3.10 组队协调流程

当执行需要组队的战斗任务时，09-运行控制中心 协调主号与小号协同作战：

```
主号战斗任务开始前 → 检查 task_config.teaming 是否为 true
  │
  ├── 需要组队：
  │     ├── 1. 调 15-账号管理模块.get_teaming_partners(group)
  │     │     → 获取同 group 的小号列表
  │     │
  │     ├── 2. 调 15-账号管理模块.prepare_teaming(task_name)
  │     │     → 依次唤醒小号、完成前置操作
  │     │     → 返回 {sub1: True, sub2: True} 就绪状态
  │     │     → 每个小号准备完成后发布 teaming_prepared 事件
  │     │     → 09 收到后调 _on_teaming_prepared() 确认就绪
  │     │
  │     ├── 3. 根据 team_host 配置选择组队模式
  │     │     ├── 模式A（主号带队）：
  │     │     │    主号创建队伍 → 发布 coordinate_action 协调小号加入
  │     │     │    09 收到 coordinate_action 事件后调 _on_coordinate_action()
  │     │     │    → 切换到小号 → 执行加入操作（接受邀请/申请入队）
  │     │     │    → 切换回主号 → 开始战斗
  │     │     └── 模式B（小号开车）：
  │     │          小号创建队伍 → 主号被动加入（CoopPassive）
  │     │          09 调 _on_coordinate_action() 协调小号创建
  │     │
  │     └── 4. 进入 BattleLoop 战斗循环
  │
  └── 不需要组队：正常执行
```

> **事件驱动协调**：09 不直接调用小号设备操作。`prepare_teaming()` 由 15-账号管理模块 切换账号并发布 `teaming_prepared` 事件，09 订阅后通过 Executor 执行具体识图/点击。`coordinate_action` 同理——09 收到事件后通过 `_on_coordinate_action()` 响应，使用 `_account_mgr.switch_to()` + `_executor.click_image()` 完成实际组队操作。
>
> **与扫描线程的关系**：组队操作期间扫描线程被 `_scanner_lock` 阻止（non-blocking acquire 失败则跳过本轮），避免扫描线程与组队线程同时操作设备产生冲突。

## 四、重点功能

### 4.1 三线程协同调度

填充线程 + 执行线程 + 扫描线程三个独立线程协同工作。填充线程只负责到期任务入队（不阻塞执行），执行线程专注任务执行+场景检测+错误恢复，扫描线程独立维护小号状态。三线程通过 `_task_queue`（线程安全队列）和 `_stop_event`（threading.Event）通信，无锁竞争问题。

### 4.2 自适应休眠

填充线程无到期任务时递增休眠时间（2~10 秒），执行线程队列空时休眠 0.5 秒，扫描线程每 30 分钟执行一轮。所有休眠分段检查 `_stop_event`，确保用户停止时快速响应。

### 4.3 错误恢复与保护模式

任务失败后自动执行场景检测→恢复路径选择→保护模式的完整恢复链路。单次任务最多重试 3 次（含恢复后的重试），全部失败则跳过任务，避免死循环。未知场景进入保护模式（通用退出序列：关弹窗→返回键）。

### 4.4 暂停/恢复控制

支持用户随时暂停和恢复运行。暂停时填充线程停止入队新任务，执行线程完成当前任务后休眠，扫描线程继续独立运行。恢复后自动回到正常运行状态，无需重新初始化。暂停期间 `_state` 通过 `_state_lock` 保护，所有线程通过分段休眠（每段 1s）检查状态变化，确保恢复响应延迟不超过 1 秒。

### 4.5 组队协调

支持主号与小号之间的组队战斗协调。通过事件驱动模型（`teaming_prepared` / `coordinate_action`）实现账号切换和组队操作，09 不直接操作小号设备，而是通过 15-账号管理模块 切换账号后由 Executor 执行具体识图/点击。组队期间扫描线程被 `_scanner_lock` 阻止，避免设备操作冲突。

### 4.6 沙盒模式

支持不实际执行点击的试运行模式，用于验证新任务脚本：

- 启动时通过 UI 切换沙盒模式开关
- 沙盒模式下 14-执行器 的 `set_dry_run(True)` 生效，所有操作仅记录日志，不执行 ADB 点击
- 调度循环正常执行（build_schedule → 入队 → 出队 → execute），但所有实际操作被拦截
- 日志中标注 `[沙盒]` 前缀，便于区分真实运行
- 方法一览：`executor.set_dry_run(True)` / `executor.is_dry_run()`
- 可用于验证任务流程、测试新模块、调试场景恢复

### 4.5 通知推送

在以下时机自动推送通知：

| 触发时机 | 通知级别 | 内容 |
|---------|---------|------|
| 所有任务完成 | success | "所有任务已完成" |
| 任务连续失败 | warning | "xx任务连续失败N次" |
| 已达运行上限 | info | "已达今日上限，自动停止" |
| 定时停止 | info | "已到设定停止时间" |
| 脚本异常崩溃 | error | "脚本异常退出，请检查" |

通知方式通过配置可选：桌面弹窗 / 声音提示 / Webhook。

### 4.6 外部调度器复用

MainWindow 启动时已初始化 Scheduler 并发布初始日程到 UI。ScriptWorker 可复用该实例（通过 `scheduler` 参数注入），避免重复加载配置和状态不一致。

## 五、实现思路

### 5.1 模块结构

```
core/
├── run_state.py              ← RunState 枚举 / RuntimeProgress / Finding 数据类
```

### 5.4 核心流程

**启动链路**：
1. MainWindow._on_start() 创建 ScriptWorker 实例
2. 注入 Scheduler（复用已有实例）
3. worker.start() → QThread 启动 → run() → _execute()

**触发监控启动**：`_start_run()` 中在启动三线程前调用 `_trigger_watcher.start()`——
收集 `repeat.type=trigger` 任务的 `trigger_templates` 识别列表并启动常驻监控线程。
识别命中 → 发布 `trigger_detected` → 05-时间调度模块 订阅后 `update_next_run(name, now)` → 填充线程拾取入队。

**运行链路**：
1. Step1~Step8 顺序执行初始化
2. 登录成功后启动三线程（_filler_loop / _executor_loop / _scanner_loop）
3. 填充线程：build_schedule → get_next_task → 到期入队 _task_queue
4. 执行线程：_task_queue 出队 → 弹窗扫描 → 执行 → mark_done

**停止链路**：
1. 用户点击停止 → worker.stop()
2. _stop_flag = True
3. 循环检查到停止 → 退出循环
4. save_state() → finished_signal

### 5.5 关键设计

- **QThread 子类**：ScriptWorker 继承 QThread，通过 pyqtSignal 与主线程 UI 通信
- **线程安全停止**：`_stop_flag` 由 `QMutex` 保护，循环中每步检查
- **任务注册获取**：通过 `TaskRegistry.get(name)` 获取已注册的任务实例，由 **04-任务执行引擎** 统一管理任务发现和注册（`TaskRegistry.discover_tasks()`）
- **Scheduler 注入**：支持外部复用 Scheduler 实例，避免重复加载配置
- **组队协调的事件驱动解耦**：09 不直接操作小号设备，通过 `teaming_prepared` / `coordinate_action` 事件编排组队流程，实际设备操作由 15-账号管理模块 切换账号、14-执行器模块 执行识图点击。09 保持编排者角色，不膨胀为"全能控制器"
- **暂停不中断原则**：暂停时填充/执行线程休眠但扫描线程继续运行，所有线程通过分段休眠检查 `_state` 变化。`try-finally` 确保 `_scanner_lock` 和 `_state_lock` 在组队流程异常时正确释放，避免死锁

| 发布 `\"task_done\"` 事件 | **08-事件通信总线** → **11-用户界面模块** | UI 清除当前任务+刷新队列 |
| 发布 `\"run_started\"` / `\"run_paused\"` / `\"run_stopped\"` / `\"run_limit_reached\"` | **08-事件通信总线** → **11-用户界面模块** | UI 更新运行状态栏 |
